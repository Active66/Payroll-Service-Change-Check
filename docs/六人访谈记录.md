  推导：事实明确更新时须同时记录业务发生时间和系统接收时间，过期来源不能覆盖已确认新版本；读取失败保留快照并标记时间、提示人工核查。现场又存在群消息先行、回填时间不等于发生时间的习惯，说明单时间戳不可靠。但“过期”指来源晚到还是旧数据覆盖已确认版本，两种口径尚未定，更新频率也无核实结论。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：由傅景先明确过期场景定义，再用脱敏样本构造晚到与覆盖两类案例各若干条，验证双时间戳加确认状态能否区分；验收看两类案例是否都能定位来源且不误判。
- REQ-3 一线需要一页缺项清单加来源位置，而非泛化摘要
  依据：dlg-fsg-payroll-f15、dlg-fsg-payroll-f10、dlg-fsg-payroll-f33、dlg-fsg-payroll-f14
  推导：一线明确表示需要一页缺项清单和对应来源位置以减少返工，不需要长摘要；现场困难是变更邮件与月度表格难以追溯到同一版本。数据质量检查也要求问题记录保留原行。但清单具体字段、由谁生成、以哪份原始记录为准尚未核实，且系统建议不能覆盖原值或省略确认。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：用脱敏样本试做一页缺项清单原型，由林亦舟实际核对并记录返工次数变化；验收看清单能否覆盖其提出的缺项且每条可回溯来源，人工确认环节保留。
- REQ-4 交接必须列明最新版本、未结项与截止时间，并登记责任人
  依据：dlg-fsg-payroll-f23、dlg-fsg-payroll-f25、dlg-fsg-payroll-f24、dlg-fsg-payroll-f20
  推导：事实要求交接时列明最新版本、尚未确认事项和截止时间，不能只发“已处理”；跨团队变更需登记责任人，未确认项不能归到对方名下；版本采用有效期与确认状态两条件，作废保留原因。但责任清单模板、登记载体与签认人尚未核实，且一线习惯先群消息后补表，执行落地存在偏差风险。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：唐映秋先出交接清单模板草案，在一个批次内试运行，统计未结项遗漏与责任归属争议次数；验收看每次交接是否可追溯到接收人、版本与未结项。
- REQ-5 跨团队先对齐时效与二次确认窗口的目标，再谈工具
  依据：dlg-fsg-payroll-f50、dlg-fsg-payroll-f53、dlg-fsg-payroll-f51
  推导：事实指出客户经理重视时效、复核团队需二次确认窗口，目标未对齐就上工具会把矛盾固化；同一变更单的数量、状态、截止时间须按原始记录核对，而非比较两张汇总表。评估需同时看工时、返工次数与确认完整率。但各团队优先级由谁定、以哪份原始记录为准尚未核实。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：叶书组织一次目标对齐会，明确原始记录基准与二次确认窗口时长，形成书面口径；验收看双方是否认可同一份原始记录及三项评估指标取数来源。
- REQ-6 验收与兜底：40条脱敏样本全覆盖来源定位，无法确认即进人工队列
  依据：dlg-fsg-payroll-f42、dlg-fsg-payroll-f44、dlg-fsg-payroll-f41、dlg-fsg-payroll-f02
  推导：事实明确演练质量标准为40条脱敏样本核对、所有金额差异有来源定位、每条结果关联来源与人工复核记录；无法确认版本或关键字段时进人工队列，必要时暂停试点，不能默认通过；正式结论须授权人员确认。但40条样本由谁提供、脱敏程度、复核记录由谁签认尚未核实，验收无法签字。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：顾明岚确认样本提供方与脱敏标准，傅景确认签认人；先跑40条样本，验收看来源定位是否全覆盖、人工队列是否被触发并留痕。此为演练验收，不代表真实业务通过。
