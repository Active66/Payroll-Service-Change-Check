01系统定位与边界

1.1 一句话定位

本系统是员工薪酬变更的受理、核对与留证中枢：它不生产薪酬主数据，也不计算工资，但它是唯一有权决定"某条变更能否进入本期发薪"的地方。

换句话说，它坐在数据流的关键卡口上，是准入控制器，不是数据仓库，也不是薪酬引擎。

1.3 范围内（做什么）

  • 变更单的创建、受理、撤回、冲正与全生命周期状态管理
  • 按配置化规则对变更单做自动核对，产出可解释的判定结论
  • 差异的分级、分派、处置、豁免与关闭闭环
  • 发薪批次准入判定：给出"可进入本期"的变更集与不可进入的原因清单
  • 核对结果快照与员工薪资时点快照，支持复算与举证
  • 员工自助：指定字段的变更发起与工资条查看
  • 政策参数库维护（社保公积金上下限、比例区间、个税扣除标准）
  • 全链路审计与导出管控

1.4 明确不做（Out of Scope）

  • 不做薪酬计算——不实现计税算法、不生成应发实发，只核对输入数据的正确性
  • 不接管员工主数据——员工基本信息仍以 HR 系统为权威源，本系统仅持有核对所需快照
  • 不做银行直连——只生成符合银行模板的加密代发文件，不承担银企对接
  • 不做个税申报报送——只生成申报数据文件，报送在税务端完成
  • 不做考勤核算——考勤数据作为输入接收，不校验考勤规则本身
  • 不做劳动合同与人事流程——入离调转的审批仍在原系统
  • P0 不做规则引擎——先做配置化比对，Drools 类引擎留作 P2 的替换选项

3.3 关键不变量

这些是系统的"物理定律"，实现时可以妥协交互，但不能妥协它们。每一条都应有对应的自动化测试守住。

I1
无核对则不发薪。任何进入发薪批次的数据，必须存在核对通过记录或有效期内的豁免记录。系统不提供"跳过核对"的开关。
I2
已生效不可改。已生效变更的任何字段不得原地更新，只能追加冲正单。冲正单自身也要走核对与审批。
I3
同键唯一生效。同一员工、同一字段、同一生效月份，最多存在一条生效记录；重入的其余记录必须被显式覆盖或驳回并留痕。
I4
追溯必标注。生效日期早于当前薪酬周期的变更，一律标记为追溯件，走独立审批路径并强制要求业务事由。
I5
员工端冻结期。员工自助提交的变更，生效时间不得早于提交时间加上冻结期（银行账号默认 3 个自然日，且须避开发薪日 T-3 至 T+1）。
I6
结论必须可溯源。每条核对结论必须绑定规则集版本号与政策参数版本号；缺少任一项时判定为"不可判定"，按 L3 阻断处理，不得默认通过。
I7
审计只追加。审计表在数据库层撤销 UPDATE / DELETE 权限，应用层无删除接口。任何"清理日志"需求一律拒绝，只能归档到冷存储。
I8
快照不可变。快照生成后即冻结，内容哈希写入审计链；重建快照必须生成新版本号，不得覆盖旧版本。

4.2 规则配置模型（声明式 DSL）

D4 选的是配置化字段比对，因此规则不是代码，而是可版本化的声明式文档。判定逻辑全部收敛到一个 RuleEvaluator 接口，将来换规则引擎只需替换该实现。

{
  "id": "R4-SI-BASE-RANGE",
  "name": "社保缴费基数上下限校验",
  "version": 3,
  "scope": { "legalEntity": "*", "region": "310000", "payrollGroup": "*" },
  "when":   { "field": "socialInsuranceBase", "changed": true },
  "assert": "value >= policy('SI_BASE_MIN', region, period)
             && value <= policy('SI_BASE_MAX', region, period)",
  "level":  "L3",
  "slaHours": 24,
  "message": "社保基数 ${value} 超出 ${region} ${period} 区间 [${min}, ${max}]",
  "effectiveFrom": "2026-07-01"
}

约束：assert 只允许引用入参、上下文与 policy() 函数，禁止跨表查询与副作用；每条规则必须给出可读的 message，否则视为规则不可交付——员工和管理员看到结论时必须知道"哪条规则、为什么"。

6.1 文件通道规范

  • 幂等键：法人 + 薪酬周期 + 文件类型 + 文件内容哈希。重复上传判定为同一批次，不重复入库
  • 模板注册表：每个文件类型维护多个版本，绑定生效日期区间；解析时按业务日期选版本，禁止"最新版本一刀切"
  • 列映射配置：源表列名 → 系统字段的映射可配置，避免因上游改列名而改代码
  • 干跑预检：正式导入前必须支持"只解析不入库"，输出错误行号与单元格定位（如 第 42 行 · D 列 · 银行卡号校验失败）
  • 补偿机制：文件批次可整批回滚（软删 + 标记），但已产生审计事件不可撤销
  • 人工通道视为一等公民：考虑到行业现实，上传界面必须支持断点续传、失败重试、错误行下载修正后重传

07双时态与快照

7.1 建模规则

  • 所有业务实体表统一携带 valid_from / valid_to（业务生效区间，左闭右开）
  • 所有业务实体表统一携带 recorded_at（系统记录时间，单调递增，只追加）
  • 关键字段禁止 UPDATE，变更一律 INSERT 新版本并把上一版本 valid_to 置为切换点
  • 查询统一通过 asOf(businessTime, systemTime) 接口，禁止业务代码直接写裸 SQL 读表
这条最容易做错：很多团队只加了 valid_from / valid_to 就自称双时态，实际上仍用 UPDATE 改历史行。真正的双时态是"任何时刻发生的事，都能区分'事情本身何时生效'和'我们何时才知道它'"，这两个时间轴缺一不可——追溯调薪恰恰依赖后者。

核对输入快照每次核对任务开始时保留 5 年，保证结论可复算
核对结论快照任务完成时保留 10 年，作为准入证据
员工时点快照每次发薪周期结束时保留 10 年，争议举证主证据
政策参数快照参数版本发布时永久保留，历史结论复算依赖

指标基线值设计余量

8.2 性能指标

操作目标说明

8.3 可用性

  • 发薪窗口（每月 T-3 至 T+2）：99.9%，窗口内禁止计划内变更发布
  • 非发薪窗口：99.5%
  • RPO < 15 分钟，RTO < 2 小时；核对任务失败可重跑，属可恢复故障
  • 降级策略：核对服务不可用时，禁止降级为"默认通过"，只能挂起并提示稍后重试——这是 I1 的直接要求

8.4 安全与合规（对齐等保三级）

控制项要求
传输加密全站 TLS 1.2+，文件通道另行加密（信封加密，密钥与数据分离传递）
存储加密证件号、银行账号、薪资、家庭信息字段级加密（AES-256-GCM），密钥托管 KMS，按法人分密钥，年度轮换
脱敏默认展示脱敏；查看明文需二次授权并逐次记录；列表页永不出现明文
授权RBAC + ABAC（法人 × 薪酬组 × 字段 × 时间窗）；权限变更本身产生审计事件
身份管理员强制双因子；员工端实名核验（证件尾号 + 短信，可选人脸）
审计append-only + 哈希链；数据库层撤销 UPDATE/DELETE 权限；审计与应用库物理分离
导出管控导出需审批、加水印（含操作人与时间）、限次数、全量留痕；禁止整表导出无审批
留存薪资与核对记录：在职期间 + 离职后 10 年；审计日志：10 年；快照：见 7.3
销毁到期数据走审批后归档至冷存储，不做物理删除；销毁申请须审计员复核

09架构方案

9.1 逻辑分层

接入层
Web 管理端 · 员工端 H5（企业微信内嵌）· 文件通道（上传/下载/回盘）· OpenAPI · 统一认证与网关
应用层
变更域（受理 · 冲正 · 生命周期）　核对域（规则执行 · 结论产出）　审批域（路由 · 签批）　差异域（分级 · 分派 · 豁免）　员工自助域（申请 · 工资条）
平台层
规则配置中心 · 政策参数库 · 文件解析引擎 · 快照服务 · 审计服务 · 通知服务 · 作业调度
数据层
业务主库（读写分离）· 快照库 · 审计库（独立实例）· 对象存储（附件/原始文件/快照归档）· 缓存 · 消息队列

9.2 四个关键设计决策

决策选型理由与代价
系统形态模块化单体 + 独立 Worker事务边界集中在变更单与批次准入，微服务会引入分布式事务却换不来收益。代价：模块边界靠约定与包结构维持，需定期做依赖检查
核对执行异步事件驱动变更单提交后发事件，Worker 消费后回写结论。核对绝不写在提交事务里，否则长事务与阻塞会拖垮发薪窗口
事件可靠性事务性发件箱（Outbox）业务写入与事件写入同事务，独立投递器负责发送，避免"业务成功、事件丢失"导致变更永不核对
规则判定单一 RuleEvaluator 接口D4 阶段用表达式解释器（Aviator / SpEL），语义统一；将来若升级为规则引擎，只替换该接口实现

9.3 技术选型建议

层建议说明
后端Java 17 + Spring Boot 3企业内易招人、审计友好、生态成熟
数据库PostgreSQL 15+ 或 MySQL 8倾向 PG：窗口函数、范围类型对双时态查询更友好
消息RabbitMQ 或 RocketMQ量级不大，可靠性优先于吞吐
对象存储MinIO（私有化）/ OSS存附件、原始文件、快照归档
前端Vue 3 + Element Plus管理端表格与表单密集，组件生态成熟
员工端H5，企业微信内嵌覆盖率高，不必另做 App
密钥与加密KMS（云托管或私有 Vault）字段级加密的密钥不得与数据同库
可观测结构化日志 + 指标 + 链路追踪审计日志与运行日志分开存储，前者不可删

9.4 部署形态

  • 应用双实例起步，Worker 按法人分片消费，可独立扩容
  • 审计库独立实例，与业务库物理隔离，只接受追加写
  • 发薪窗口前 3 天进入"冻结发布期"，仅允许紧急补丁，且需双人复核
  • 不依赖公有云专属能力，保留私有化部署可能性（合规审查的常见要求）

11假设与风险登记

11.1 关键假设（若不成立需重新评估）

编号假设不成立时的后果
A1薪酬计算在既有系统完成，本系统不承担算薪若需自建算薪，整体方案升维为 D 类，工期翻数倍
A2员工总数不超过 3 万，法人不超过 20超出需引入分片与独立对账集群，架构与运维成本显著上升
A3HR 系统可提供稳定的月度全量文件若只能提供增量或无文件，需先建数据同步基线，P0 延期
A4各地社保公积金政策参数可被结构化维护若政策以人工裁量为主，R4 类规则只能降级为提示，核对价值打折
A5存在明确且唯一的规则口径责任人无 Owner 时规则将反复变更，核对结论失去公信力，这是最高概率的项目失败原因

11.2 风险登记

编号风险等级缓解措施
K1上游数据质量差，差异噪声淹没业务高P0 先做数据质量基线报告，把"系统性脏数据"与"真实业务差异"分开；噪声规则先降级为 L1
K2业务为赶发薪绕过系统，走线下通道高系统必须比线下更快（单证提交 → 结论 < 1 分钟）；同时把"绕过"本身做成需高管审批的例外
K3员工换卡被用于诈骗（社工改卡）高冻结期 + 发薪窗口禁改 + 大额首笔人工复核 + 变更短信双通知（旧号与新号同时告警）
K4等保三级要求带来额外改造，工期被低估中加密与审计在 P0 就进地基；安全评审前置到设计阶段，不留到上线前
K5集团内跨法人调岗导致社保转移与工龄衔接复杂中员工主体变更设计为"一人多任职"模型，而非简单改法人字段
K6规则越配越多，最终无人敢改中规则总量设上限并定期清理；每条规则必须有 Owner 与最近一次复核日期
