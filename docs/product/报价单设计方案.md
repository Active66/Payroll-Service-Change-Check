# 报价单设计方案

> **依据**：FDE 交付的九个成本科目（模块 2 · 成本核算）
> **适用**：AI 应用类项目、FDE（Forward Deployed Engineer）交付模式
> **配套实例**：薪酬服务变更核对 · AI 数智化改造（见第 6 章）
> **文档性质**：报价单设计规范 + 可套用的模板，不是某一份具体报价

---

## 0. 一句话结论

现有报价单的问题不是数字算错，是**只报了九分之一**。

本方案做三件事：

1. 把 9 个成本科目全部条目化，每个科目落成客户看得懂、可计量、有交付物凭据的一行；
2. 把表外三层（管理分摊 / 风险准备 / 利润）显性摊进去，不再由乙方默默承担；
3. 输出**双版本报价单**——客户可见版（只列条目与金额）与内部成本版（含科目成本、摊薄、实际毛利）。

最终目的不是报得更贵，而是**让价格有锚**：当客户能逐条比对"这笔钱买到了什么"，比价基准就从"人头单价"变成"交付范围"。

## 1. 问题诊断：为什么报价总被压

### 1.1 现状：单科目报价的三个结构性缺陷

| 缺陷 | 表现 | 后果 |
|---|---|---|
| **计价单位单一** | 全部折成"开发 XX 人天" | Token、算力、数据资产、合规测评这些非人力成本无处安放，只能塞进人天里或干脆不报 |
| **无表外三层** | 报价只覆盖直接人力 | 管理分摊、风险准备被当成"毛利"吃掉，看着有 20% 利润，实际是负的 |
| **无"不含项"** | 只写做什么，不写不做什么 | 验收阶段范围无限扩张，变更没有计价依据，只能免费做 |

### 1.2 算术上的真相

以第 6 章实例测算（136 人天等值 × 4,000 元）：

| | 金额 |
|---|---|
| 只报"开发人天" | 544,000 |
| 实际成本（直接 + 售前 + 管理 + 风险） | 704,000 |
| **实际毛利** | **−160,000（毛利率 −29%）** |

客户还在说"贵"。这就是图里那句话的物理含义：**不是因为数字算错了，而是只报了九分之六的直接人力，剩下三个科目和三层摊薄你自己扛了。**

### 1.3 被漏掉的三类钱

- **已经花掉但没进报价的钱**：售前方案、驻场调研、POC 演示（C01）——没中标也照花。
- **会随规模膨胀的钱**：Token 调用、向量库、第三方 API（C07）——今天报固定价，明天客户用量翻三倍。
- **永远收不回来的钱**：风险准备（需求变更、验收争议）——不预留，就等于承诺无限责任。

## 2. 设计目标与五条原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **科目全显性** | 9 个科目 + 3 层摊薄，任何一个不能在报价单上"消失"（可以不单列，但必须进基数） | 把算力成本摊进人天单价 |
| **单位可计量** | 每个条目有明确计量单位：人天 / 单据类型 / 千次调用 / 月 | "数据治理：一项" |
| **条目客户可读** | 条目名用客户的语言，不用内部工序名 | "ETL 开发" → "把三个来源的同一张单对到一起" |
| **波动项单列** | 用量会变的科目必须独立成行，不打包进固定价 | 算力写进"实施费" |
| **边界可执行** | "不含项"要具体到能据此拒绝需求 | "不含额外需求" |

---

## 3. 报价单总体结构：三层

```
L1 科目层   9 个成本科目 + 3 层摊薄        ← 决定"报什么"
L2 条目层   可报价的最小单元（每个科目 1~n 条）  ← 决定"怎么拆"
L3 单价层   元/人天、元/单据类型、元/千次、元/月  ← 决定"怎么算"
```

只有 L1 会出现在客户面前；L2 是客户真正逐行比对的层级；L3 是谈判时可以单独让步的杠杆（**降单价不降范围，或降范围不降单价，二者只能选一个**）。

## 4. 九个成本科目：报价条目化

### 4.1 科目总表

| 编码 | 客户可见条目名 | 计量单位 | 计量口径 | 交付物凭据 | 计价模式 |
|---|---|---|---|---|---|
| C01 | *（不进客户版）* | 人天 | 立项前实际投入 | 售前记录 / POC 记录 | 摊入管理分摊 |
| C02 | 业务诊断与场景梳理 | 人天 / 诊断包 | 访谈场次 × 角色数 | 诊断报告、可落地清单 | 固定价 |
| C03 | 方案与架构设计 | 人天 | 架构文档页数 / 评审轮次 | 架构方案、验收标准 | 固定价 |
| C04 | 数据与知识资产建设 | **元/资产单元** | 单据类型 × 源系统数 | 资产清单、口径说明书 | 固定价 + 变更 |
| C05 | 集成与工程实施 | 人天 / 接口数 | 接口数 × 老系统系数 | 接口文档、联调记录 | 固定价 |
| C06 | 评测与安全合规 | 用例数 / 人天 | 测试用例条数 × 轮次 | 测试报告、合规清单 | 固定价 |
| C07 | 算力与模型调用 | 元/千次、元/月 | 实际调用量 | 用量账单（月度） | **按量 / 预付额度** |
| C08 | 部署上线与培训 | 人天 / 场次 | 角色数 × 场次 | 手册、签到表、演练记录 | 固定价 |
| C09 | 运维与持续优化 | 元/月 | 服务等级 × 月数 | SLA 报告、迭代记录 | **订阅** |

> 设计要点：C01 不进客户可见版——客户不会为"你没中标也花的钱"付费，但这笔钱必须从其他科目的管理分摊里回收。**看不见 ≠ 不存在。**

### 4.2 逐科目口径与话术

**C01 售前与机会成本**
不单列，按年度售前总投入 ÷ 预计中标单数，摊入每个报价的管理分摊。内部版必须记录：本单消耗售前 6 人天。
*坑*：把它写进客户版叫"方案费"，会被理解为"还没干活就收钱"。

**C02 诊断与场景梳理**
这是 FDE 的核心工时，也是最难被认可价值的部分——因为它不产出代码。对策：交付物必须是**客户能拿去开会的东西**（诊断报告、优先级清单），不是会议纪要。
*坑*：客户会说"这个我们内部也能做"。回应：内部做的是"我们有什么问题"，我们做的是"哪个问题现在能被 AI 解决、哪个不能"。

**C03 方案与架构设计**
必须包含**验收标准定义**——这是把 C03 从"画图"变成"定规则"的关键。谁定义验收，谁定义范围。
*坑*：只交付架构图，客户认为你只是"画了个框图"。

**C04 数据与知识资产建设**
**2026 年最大的变量，也是报价单上最该被单独算清楚的一项。**
按"资产单元"计价（一类单据 × 一个源系统 = 1 个单元），而不是按人天——因为单元数翻倍时工作量不是线性增长，而是指数增长（两两归并）。
*坑*：按人天报，客户会砍人天；按单元报，客户砍的是范围，你能守住单价。

**C05 集成与工程实施**
给接口设**系数**：标准 SaaS/开放 API = 1.0，私有化部署中间件 = 1.5，老系统无文档 / 需人工导出 = 2.0~2.5。
*坑*：不设系数，客户会拿"接个接口而已"来压价，然后给你一个只有截图没有文档的老系统。

**C06 评测与安全合规**
必须单独成行，且不可砍。含：幻觉测试、越权与注入测试、审计留痕验证、数据分级、密评/等保配合。
*坑*：被砍掉后客户上线出事故，责任仍在乙方。**这一行是保险，不是成本。**

**C07 算力与模型调用**
永远不打包进固定价。三种模式：①预付额度包（推荐）②按量后付 ③客户自采（乙方只做接入，单价下调但责任转移）。
*坑*：报固定价 + 客户用量超预期 = 你替客户承担了业务增长的算力成本。

**C08 部署上线与培训**
计量单位是"角色数 × 场次"，不是"1 次培训"。客户方人员的适应成本也算在这里（要写进假设：客户需提供 X 人 × Y 小时）。
*坑*：写完手册就走，客户用不起来，运维工单从第一天开始爆。

**C09 运维与持续优化**
从"一次性收入"走向"持续收入"的地基。报价单里必须出现，哪怕只是 1 个月试运行——**它的存在本身就是定价权**。
*坑*：免费送一年运维，等于把未来 12 个月的不可控成本贴现进了本期报价。

## 5. 表外三层

| 层 | 建议比例 | 计算基数 | 说明 |
|---|---|---|---|
| **管理分摊** | 12% ~ 18% | 直接成本 | 销售、行政、房租、设备、售前（C01）回收 |
| **风险准备** | 8% ~ 15% | 直接成本 | 需求变更、验收争议、返工；**首次合作的 AI 项目取上限** |
| **利润** | 15% ~ 25% | 直接成本 + 上述两层 | 低于 15% 不建议接；高于 25% 需有独占性理由 |

计算顺序（不可颠倒）：

```
直接成本 D
  + 管理分摊 = D × 15%
  + 风险准备 = D × 10%
  ─────────────────
  = 小计 B
  + 利润     = B × 20%
  ─────────────────
  = 不含税报价
  × (1 + 税率 6%)
  = 含税报价
```

> 常见错误：把利润直接加在"直接成本"上，而不是加在"已含分摊与风险的基数"上——这样名义 20% 利润，实际利润率只有 12%~14%。

## 6. 实例化：薪酬服务变更核对 · AI 数智化改造

> **本章所有金额为示例参数**，用于演示报价单结构。实际执行需按当年人天单价与工作量重新校准，不构成对外报价。

### 6.5 不含项清单（12 条）

这一段比"含什么"更重要，**它是拒绝需求的合法依据**：

1. 不回写客户任何业务系统（只读边界）；
2. 不做自动审批、不做自动放行、不设默认通过；
3. 不推算业务发生时间，只记录系统接收时间；
4. AI 建议不覆盖原值，仅作候选；
5. 不代客户执行数据录入与补录（只出缺项清单，由一线补录）；
6. 不含客户侧系统改造（邮件、台账、文件库的接口开发由客户方负责）；
7. 不含等保测评、密评的第三方费用；
8. 不含客户方终端、网络、账号权限的改造；
9. 不含客户决策延迟造成的等待成本与工期顺延；
10. 不含超出约定单据类型 / 源系统范围的新增对接；
11. 不含模型微调训练（如需另立变更单）；
12. 不含现场驻场差旅（按实报实销，或按 1,200 元/人天包干）。

## 7. 计价模式与组合

| 模式 | 适用科目 | 优点 | 风险 |
|---|---|---|---|
| **固定包干** | C02 C03 C06 C08 | 客户易接受，便于比价 | 需求蔓延时乙方吃满 |
| **按单元** | C04 C05 | 与工作量真实相关，砍的是范围不是单价 | 单元定义必须在合同里写死 |
| **按量后付** | C07 | 完全转移波动风险 | 客户不愿签，需预付额度兜底 |
| **订阅** | C09 | 形成持续收入 | 首年容易被要求"赠送" |
| **里程碑付款** | 全部一次性项 | 现金流可控 | 里程碑定义不清会变成验收争议 |

**推荐组合**：一次性 = 固定包干（C02/C03/C06/C08）+ 按单元（C04/C05）；持续 = 按量预付（C07）+ 订阅（C09）。

**付款节奏建议**：30% 启动 / 30% 架构评审通过 / 30% 上线验收 / 10% 运行 30 天后。

## 8. 三档报价：用范围做锚，不用折扣做锚

| | **Lite · 诊断与规则校验** | **Standard · 全流程核对**（推荐） | **Full · 含托管运维** |
|---|---|---|---|
| C02 诊断 | ✓ | ✓ | ✓ |
| C03 架构 | 简化版 | ✓ | ✓ |
| C04 数据资产 | 仅主数据 5 类 | 8 单元 + 清洗 | 8 单元 + 清洗 + 季度复核 |
| C05 集成 | 仅 1 个源 | 4 个接入点 | 4 个接入点 + 冗余通道 |
| C06 评测合规 | 基础用例 | 全量用例 | 全量 + 年度复测 |
| C08 上线培训 | 单角色 | 3 类角色 | 3 类角色 + 跟班 2 周 |
| C07 算力 | 客户自采 | 预付额度 | 预付额度 + 用量优化 |
| C09 运维 | 无 | 6 个月 | 12 个月 + 4h SLA |
| **不含税** | 约 340,000 | 816,000 | 约 1,130,000 |

三档的真正作用是**让中间那档显得合理**，而不是真的卖 Lite。Lite 的存在是为了证明 Standard 不贵，Full 的存在是为了证明 Standard 够用。

## 9. 报价单版式规范

### 9.1 必填字段（明细行）

| 字段 | 必填 | 说明 |
|---|---|---|
| 行号 | ✓ | 客户提变更时引用此号 |
| 科目编码 | 内部版必填 | C01~C09，客户版隐藏 |
| 条目名称 | ✓ | 客户语言，不带内部工序名 |
| 交付物 | ✓ | 可验收的实体，不是"服务" |
| 计量单位 | ✓ | 人天 / 单元 / 千次 / 月 |
| 数量 | ✓ | 数字，不写"若干" |
| 单价 | ✓ | 客户版可只给包干总价 |
| 金额 | ✓ | 与数量 × 单价一致 |
| 计价模式 | ✓ | 包干 / 按单元 / 按量 / 订阅 |
| 假设前提 | 按需 | 客户需配合的事项 |

### 9.2 禁止写法

| ❌ 禁止 | ✅ 改为 |
|---|---|
| 开发费：80 万 | 按 6 个条目分列，每行有交付物 |
| 数据治理：1 项 | 8 个资产单元 × 8,000 |
| 接口对接：按实际 | 4 个接入点 × 12 人天，老系统系数 2.0 |
| 运维：赠送一年 | 订阅 8,000/月，首月免费试用 |
| 其他费用：另计 | 明确列出 C07 预付额度与超出单价 |

### 9.3 版式建议

- **一页纸原则**：明细不超过 10 行，超过就说明拆得不够，客户会失去耐心；
- **金额右对齐、科目左对齐**，让客户的眼睛自然落在"范围"而不是"总价"；
- **不含项独占一页**，且放在明细之后、签章之前——客户一定会看这一页；
- **报价有效期 30 天**，且注明"人天单价随年度调整"。

## 11. 商务红线（8 条）

1. **不报单一总价**——至少 6 行明细，否则必然被拆成"人头 × 天数"比价。
2. **不把算力打包进固定价**——用量是客户的业务变量，不是你的成本变量。
3. **不免费赠送运维**——赠送的运维等于把未来的不可控成本贴现进本期。
4. **不接受"先做后补合同"**——AI 项目的范围在做的过程中一定会变，没有合同就没有变更依据。
5. **不在报价阶段承诺准确率数字**——改为承诺"评测方法与验收流程"。
6. **不接"验收标准由客户单方定义"的单**——C03 的验收标准定义权是核心交付物。
7. **风险准备低于 8% 不接首次合作项目**——AI 项目的返工率高于传统开发。
8. **利润低于 15% 不接**——低价中标后用变更单找补，是行业里最坏的一种循环。

### 12.2 变更计价公式

```
新增条目金额 = Σ(新增数量 × 对应单价) × (1 + 管理分摊率) × (1 + 风险准备率) × (1 + 利润率)
```

- 变更金额 < 合同额 5%：按人天计，不套三层摊薄（降低摩擦）；
- 变更金额 ≥ 合同额 5%：必须走上述完整公式，并重新签补充协议；
- 因客户原因导致的返工：全额计价，不打折；
- 因乙方原因导致的返工：不计价，且计入风险准备消耗。
