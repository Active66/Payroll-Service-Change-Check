00先回答你的判断题：RAG 还是 LLM Wiki

0.1 三个概念先对齐

你说的"LLM wiki"我理解为：让模型把原始资料预先编译成一套实体/主题页面并持续维护，查询时直接读页面，而不是临时检索原文切片。它和 RAG、GraphRAG 不是同一层的东西，放一起比较容易比错。

范式工作方式强项致命短板（在薪酬合规场景）
朴素 RAG查询时向量召回 Top-K 切片，拼进上下文实现快、原文可引用单跳召回，覆盖不了"变更类型→制度→条款→参数→例外"的多跳链路
LLM Wiki模型预先把资料编译成结构化页面（二手转述），查询直接读页答案连贯、省 token、上下文密度高不可举证。页面是模型写的总结，和原文不一致时无法自证；制度一改，页面全面漂移
GraphRAG向量/全文召回 + 知识图谱扩展 1–2 跳 + 重排多跳、可溯源、结构化参数走精确查询需要实体关系抽取，构建成本高于朴素 RAG

0.2 判断结论

结论：主用 GraphRAG（向量 + 全文 + 图谱混合），LLM Wiki 只做"人读摘要层"，绝不做事实源。
薪酬核对的答案会被拿去当劳动争议证据、内审核查依据。凡是"模型转述的二手总结"都不能作为判定依据——这是这个域的硬约束，不是技术偏好。

三条支撑理由：

  • 可举证性——每条结论必须能指回"某份制度的第几条第几款、第几页"。LLM Wiki 的页面只有结论没有原文指针，一旦被质疑就要人去翻文件，等于没做。
  • 时效与地域——"2026 年上海社保基数上限"是精确查询，向量相似度天然不擅长；而制度有生效区间、地区维度、年度版本，这些是结构化字段与图边，不是语义。
  • 多跳性——判断一条变更是否合规，链路是：变更类型 → 适用制度 → 条款 → 引用参数 → 例外规定。单跳向量召回必然漏中间环节。

0.3 三层知识结构（这是本方案的核心设计）

层内容存储定位与铁律
L0原始制度文件（PDF / Word / 通知）对象存储 + policy_documents唯一真相源，不可变，带生效区间与版本
L1切片 + 向量 + 实体关系图pgvector + kg_entities / kg_relations检索与推理层；每个节点必须挂 doc_id + chunk_id 回溯到 L0
L2LLM 编译的人读页面（制度综述、变更类型说明）wiki_pages（P2 引入）仅供阅读与校对，答题时不得作为唯一依据，页面必须展示生成时间与来源清单

0.4 检索路由：不同问题走不同通道

这是把"看起来能用"和"真的准"区分开的地方。路由错了，再好的模型也救不回来。

问题类型示例主通道兜底与增强
精确参数2026 年上海社保基数上限是多少结构化参数表 SQL附上参数来源条款，禁止由模型口算
条款解释调薪超过薪酬带宽怎么处理向量 + BM25 混合召回图谱扩展 1 跳，带出例外规定
多跳归因这条变更为什么被阻断图谱查询（变更类型→条款链）回填条款原文片段
流程操作银行卡变更怎么提交FAQ / 操作手册向量召回—
统计分析本月阻断差异分布分析服务聚合查询不经过 LLM 生成数字，只让模型组织语言
一条硬规矩：数字不由模型产出。金额、基数、比例、条号，一律来自查询结果，模型只负责组织语言和解释。这是把幻觉率压到零的唯一可靠办法——靠 prompt 约束不可靠。

03数据模型设计

3.1 全局约定

  • 主键统一 uuid v7（时间有序，索引友好）；高频追加表（chat_messages、audit_events）用 bigserial
  • 所有表默认含 created_at / updated_at，下文不重复列出
  • 敏感字段（手机、邮箱、证件、银行卡）以 bytea 存密文，后缀 _enc，不存明文
  • 制度类表采用双时态：effective_from/to（业务生效）+ valid_from/to（系统记录）
  • 多法人隔离：所有业务表带 legal_entity_id，并启用 PostgreSQL 行级安全（RLS）兜底，防止应用层漏加条件

kg_relationsbtree(src_id) / btree(dst_id) / btree(rel_type)图扩展两个方向都要走
payroll_change_draftsbtree(legal_entity_id, status, effective_date)管理员按周期筛待办列表
全部业务表RLS + app.current_legal_entity 会话变量应用层漏加条件时，数据库兜底挡住跨法人越权
为什么不上 Neo4j：本域实体规模在 10⁴–10⁵ 量级（制度条款、地区、参数、变更类型），PG 邻接表 + 递归 CTE 两三跳完全够用，可视化在前端用 Cytoscape / AntV G6 渲染，后端不需要图数据库。多引入一套存储意味着多一套备份、监控、权限和故障域——除非实体超过百万级且需要复杂图算法，否则这是负收益。

04第一周最小验证目标

第一周的目的不是"把框架搭起来"，而是用一份真实制度，验证这条路走不走得通。CRUD 谁都会写，风险全部集中在切片质量和引用可靠性上。

4.1 一句话目标

一份真实制度文件 → 一个能多轮追问的员工问答 → 每条结论都挂着条款引用 → 前端能在图谱上点开这条引用对应的节点。
这条纵向切片打通，剩下的都是工程量的堆叠。

4.2 五天节奏

天产出验收判据
D1骨架跑起来docker-compose up 一键起 pg(pgvector+zhparser) + redis + app；/health 200；JWT 登录签发成功；alembic 首版迁移可升降
D2摄入一份真实制度《员工薪酬管理制度》+ 一份地区社保基数通知导入完成；切片保留 heading_path 与页码；index_status=ready
D3最小 RAG 问答支持三轮上下文；答案中每条结论带 chunk_id；前端可点击跳转原文并高亮
D4图谱 v0（半自动）从同一份文档抽出 30–50 个实体与关系（允许人工修正 JSON）；Cytoscape 渲染子图；点节点能看到关联条款
D5评测跑分20 条真实问题（HR 同事出题）配上期望条款，跑 tests/evals，出准确率报告

4.3 四个可量化验收指标

指标目标判定方式
引用正确率≥ 90%答案引用的条款，是否真的是该结论的依据（人工判 20 题）
要点完整率≥ 16 / 20答案覆盖期望要点，不遗漏关键例外
幻觉率0不出现原文中不存在的条款号、金额、比例、地区
端到端延迟P95 < 6s含检索、重排、生成（流式首字 < 1.5s）

4.4 明确不在第一周做

  • 管理员后台 UI（用 Swagger / 临时页面够用）
  • 图谱可视化编辑器（先手工修正 JSON，验证价值再投入）
  • 草稿状态机全流程、核对规则引擎、权限矩阵细化
  • 多法人隔离、KMS 密钥轮换、审计链哈希（P0 落表，P1 启用）
  • LLM Wiki 摘要页——它是知识运营层，等 L1 稳定后再做，顺序不能反

4.5 第一周真正的风险

不是"能不能跑通"，而是"这份制度能不能被干净地切片和引用"。
薪酬制度文件普遍存在：条款编号不连续、表格混排在正文、附件另发、修订说明与正文混在一起。如果第一周发现切片必须按人工标注的条款边界来做，那整个摄入流水线的设计要改——这才是第一周要暴露的问题，越早暴露越好。所以 D2 一定要用真实文件，不要用人造的干净样例。
