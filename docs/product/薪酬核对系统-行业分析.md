## 一页结论

| # | 判断 | 关键依据 | 对决策的含义 |
|---|---|---|---|
| **1** | **"薪酬核对"目前是一个能力模块，不是一个独立品类** | 中国薪酬管理系统市场约 63.4 亿元<sup>B</sup>，其中没有"核对"独立科目；全球同领域唯一的独立品类先例是财务对账（BlackLine，TAM 450 亿美元<sup>A</sup>），走了 20 年 | 短期不要按"新品类"定位去融资或立项，按"算薪/外包交付链上的质量层"定位，成功率高一档 |
| **2** | **需求真实，但驱动力已经从"提效"换成了"合规举证"** | 2026 年社保入税全面实施，金税四期把工资、社保、个税、银行代发拉到同一屏比对，差异率 >10% 预警、>30% 推送稽查<sup>B</sup>；社保夯实率 <70% 纳入重点监控<sup>B</sup> | 卖点从"省人力"改成"经得起查"，预算科目从 HR 工具费换成合规/风控费，天花板完全不同 |
| **3** | **供给端有明显空位：算薪引擎强 ≠ 核对层强** | 头部 HR SaaS 与外包商都强在"算得对"，弱在"证明给别人看是对的"；开源侧无同构项目，只有可复用组件 | 差异化不在算法，在**数据契约与留痕**——这恰好是外包商最难自建、SaaS 厂商最不愿下沉的那一层 |
| **4** | **技术路线上，纯 LLM 方案过不了审计关，纯规则方案过不了变化关** | 薪酬数据的错误特征是"静默、跨系统、事后暴露"，要求确定性判定；而制度版本每月在变，要求可解释的自然语言对答 | 唯一可行解是"确定性为骨、LLM 为皮"，且护栏必须是程序化复核（引用可举证、数字可溯源、无证据拒答） |
| **5** | **ROI 不要用工时节省做主论证，会被打脸** | 项目内基线"每期 300 条 / 复核 18 小时"折算下来单客户组一年仅约 0.12 FTE，即便省 60% 也不足以支撑投入 | 主论证换成三条：**差错暴露时点前移**、**举证成本下降**、**人员流动不带走知识**。这三条可与合规预算挂钩 |

## 1. 行业界定：核对层在产业链的哪个位置

### 1.1 三层结构

薪酬这件事在产业链上其实分成三段，混在一起谈就会得出"市场已经饱和"的错误结论：

```
┌───────────────────────────────────────────────────────────────────┐
│ 第一层 · 算薪（Payroll Calculation）                                │
│ 干什么：根据制度、考勤、社保基数算出应发实发                          │
│ 谁在做：ADP、SAP、北森、易路、红海云、用友、金蝶                      │
│ 成熟度：高。规则引擎是二十年积累的存量资产                            │
├───────────────────────────────────────────────────────────────────┤
│ 第二层 · 交付（Payroll Service Delivery / HRO）                     │
│ 干什么：接客户变更、登记、双人核对、出结果、发薪、申报                 │
│ 谁在做：上海外服、中智、FESCO、云生、邦芒、ADP 托管                 │
│ 成熟度：高。规模与网点是壁垒，人的经验是产能                          │
├───────────────────────────────────────────────────────────────────┤
│ 第三层 · 核对（Reconciliation & Assurance）  ← 本报告讨论的层        │
│ 干什么：证明"这次交付用的是哪个版本、谁确认的、差异在哪、能不能追"     │
│ 谁在做：几乎没有标准化产品；散落在 Excel、邮件、口头确认里            │
│ 成熟度：低。这是唯一一层还靠"人对人喊话"完成的环节                    │
└───────────────────────────────────────────────────────────────────┘
```

### 1.2 三个容易混淆的相邻概念

做行业分析时最常出现的错误，是把下面四件事当成一件事：

| 概念 | 回答的问题 | 典型产物 | 与本系统的关系 |
|---|---|---|---|
| **算薪** | 应该发多少 | 工资表 | 上游，本系统**只读**不介入 |
| **对账** | 我算的和别人算的差在哪 | 差异表 | 同构但不同域：银行/支付对账已成熟，薪酬域尚空白 |
| **核对** | **这份结果依据的是哪个版本、谁确认的** | 缺项清单 + 确认链 | **本系统本体** |
| **审计** | 过去发生的事有没有被改过 | 审计报告 | 本系统向审计提供可验证的输入 |

关键区别：**对账解决"数不一致"，核对解决"版本不一致"**。前者是计算问题，后者是治理问题。行业里 90% 的"薪酬对账工具"做的是前者，而真实痛点在后者的居多——这也是为什么很多企业买了对账工具，仍然在客户投诉时说不清"当时用的是哪一版"。

### 1.3 为什么这一层现在才值得做

三个条件在过去两年同时成熟：

1. **外部强制**：社保入税 + 金税四期，把"薪酬数据必须自洽"从道德要求变成了系统约束（详见 §3.1）；
2. **内部失配**：一个变更单要跨服务台、业务台账、文件库三个工具，且三套系统没有统一编号<sup>C</sup>，人工拼接的错行是静默的；
3. **技术可用**：文档解析与检索的成本降到可接受区间，使得"把散落的确认件读成结构化证据"第一次具备经济性。

三者缺一，这一层都做不成：只有 1 没有 3，是纯人力活；只有 3 没有 1，企业没有预算动机。

## 2. 市场：规模、结构与增速

### 2.1 自上而下：三层市场的量级

| 口径 | 2025 年规模 | 增速 | 可信度 | 说明 |
|---|---|---|---|---|
| 中国人力资源服务业营收 | **3.1 万亿元** | 同比约 +7.3%；2019–2025 CAGR 7.94% | A | 人社部口径，机构 8.1 万家、从业 111.5 万人、服务用人单位 5744 万家次 |
| 其中：人力资源服务外包 | **2.6 万亿元** | 5 年增长 73.3% | B | 占全行业 60%–70%（两来源口径不一致，取区间） |
| 其中：灵活用工 | 1.77 万亿元 | 2020 以来 CAGR 17.8% | B | 增长最快，但核对需求弱于标准薪酬 |
| 中国薪酬外包市场 | **约 800 亿元** | 同比约 +18% | B | 个税政策变化带来的核算复杂性是主要推力 |
| 中国薪酬管理系统（软件） | **63.4 亿元** | — | B | 全球同口径 243.36 亿元，中国占约 26% |
| 中国 HCM SaaS | **57.3 亿元** | 2020–2025 CAGR 20.5% | B | 2029 年预计超 100 亿元 |
| 中国人力资源软件整体 | 82.4 亿美元 | +15.3% | B | 占全球 28.6%；薪酬模块渗透率 73%，是所有模块中最高 |

**读法**：3.1 万亿的行业盘子看着大，但和"核对"直接相关的只有两块——800 亿的薪酬外包（服务费口径）和 63.4 亿的薪酬软件（License/订阅口径）。核对层不单独收费，它是这两块的成本项或溢价项。

### 2.2 渗透率：真正的增长空间在这里

| 指标 | 中国 | 美国 | 倍数 |
|---|---|---|---|
| HCM 软件渗透率 | **5.1%** | 37.3% | 7.3× |
| 云端 HCM 渗透率 | **0.8%** | 6.9% | 8.6× |
| 薪酬流程仍用表格/手工的比例 | 51% 用表格 / 19% 纯手工<sup>B</sup> | 同量级 | — |

另一边，中国 HCM SaaS 市场前五名合计仅约 49% 份额，第一名北森约 15%<sup>B</sup>——**高度分散、渗透率极低、增速双位数**，这是典型的早期市场特征。

但要注意一个反向推论：**渗透率低意味着"没上系统的人"占多数，他们要解决的是"先上系统"，不是"在系统上加核对层"**。所以核对系统的目标客户不是中小企业，而是**已经上了算薪系统、且交付链条长的中大型企业与外包服务机构**。这个客群画像决定了产品形态（私有化/专属云、对接既有系统、只读接入），也决定了销售方式（项目制而非自助订阅）。

### 2.3 参照系：财务对账是怎么长成一个品类的

这是本报告认为最有价值的一组对照。BlackLine（NASDAQ: BL）做的是财务"记录到报告"的对账与关账自动化：

| 指标 | 数值 | 含义 |
|---|---|---|
| 自述 TAM | **450 亿美元**（R2R 340 亿 + I2C 110 亿）<sup>A</sup> | 对账层可以撑起一个独立品类 |
| ARR | 6.85 亿美元（2025 Q3，同比 +7%）<sup>A</sup> | 体量不大，但极其稳定 |
| 客户数 | 4,400+，含 60%+ 的财富 500 强<sup>A</sup> | 头部客户密度极高 |
| 净收入留存（NRR） | 103%<sup>A</sup> | 黏性强，扩展慢 |
| 单客户 ARR ≥100 万美元的客户 | 从 2016 年 2 家增至 2025 Q3 的 83 家（CAGR 53%）<sup>A</sup> | "落地再扩展"路径成立 |

**三条可迁移的规律**：

1. **对账类产品增长慢但极黏**（7% 增速、103% NRR）。它不是爆发型生意，是"一旦嵌进月结流程就换不掉"的生意。
2. **价值随客户规模非线性上升**——大客户愿付的钱远超中小客户，因为差错成本不对称。
3. **它花了约 20 年才从"Excel 替代品"变成"品类"**。这提示我们：薪酬核对短期内不要指望成为品类名，先做成交付流程里的必要环节。

### 2.4 TAM / SAM / SOM 测算（参数化，可替换）

> 以下为**测算示意**，不是市场调研结论。参数取自 §2.1，替换任一参数即可重算。

```
TAM（中国 · 薪酬核对层可寻址市场）
  = 薪酬管理系统市场 × 核对能力价值占比
  = 63.4 亿元 × 15%（估算：校验/审计/留痕类能力在算薪软件中的价值占比）
  ≈ 9.5 亿元/年   ← 软件口径

  + 薪酬外包市场 × 核对相关工时占比折算
  = 800 亿元 × 8%（估算：登记/核对/出结果环节占外包交付成本的比例，非收入）
  ≈ 64 亿元/年    ← 服务成本口径（不直接形成软件收入，但是效率工具的天花板）

SAM（可服务市场：中大型企业 + 外包服务机构）
  ≈ TAM 的 30%–40%，即 3–4 亿元/年（软件口径）
  依据：仅统计已上线算薪系统、跨 3 个以上工具、月变更量 >100 条的客户

SOM（3 年可获得）
  路径 A（内部工具）：1 家头部外包商内化，年化节省 + 风险敞口折算，约 500–1500 万元当量
  路径 B（对外产品）：20–50 家中大型客户 × 20–50 万元/年 ≈ 400–2500 万元/年
```

**结论**：这是一个**亿元级软件市场 + 十亿元级服务成本池**。做内部工具，回报体现在成本与风险；做对外产品，3 年内能做到数千万营收是合理预期，但不足以支撑"平台"叙事。**立项时把预期定在这个量级，反而更容易过。**

## 3. 需求侧：五个驱动，以及一个被高估的驱动

### 3.1 驱动一：监管把"数据自洽"变成了硬约束（最强驱动）

| 变化 | 内容 | 对核对系统的含义 |
|---|---|---|
| **社保入税全面实施（2026）** | 社保征收划转税务，与个税同源管理<sup>B</sup> | 薪酬数据的错误直接变成税务风险，不再只是内部质量问题 |
| **金税四期多源交叉核验** | 工资表、个税申报、社保基数、银行代发流水同屏比对；差异率 >10% 触发黄色预警，>30% 推送稽查任务<sup>B</sup> | **对账从"企业自愿"变成"监管替你做了"**——企业需要提前自查，否则就是被动挨查 |
| **社保夯实率考核** | 夯实率 <70% 的企业列入重点监控<sup>B</sup> | 出现了一个全新的、有预算的岗位诉求："我们现在的夯实率是多少、差在哪" |
| **个税预缴规则调整** | 5000 元减除费用改为"按月申报、额度生效"，未申报即作废；新增"三险一金"扣除额与社保实缴精准比对<sup>B</sup> | 申报动作的时序错误会造成员工多缴税，属于"静默错误"，必须靠系统校验 |
| **放弃社保约定无效** | 2025 年最高法司法解释二明确任何形式"社保补贴""自愿放弃社保"约定无效<sup>B</sup> | 历史遗留的"低基数"安排集中暴露，倒逼存量数据清理 |

这一组变化的意义在于：**它把核对从"最佳实践"变成了"合规必需"，从而把预算科目从 HR 工具费挪到了风控/合规费**。前者通常几十万，后者可以上百万。这是本报告认为最值得押注的一条。

### 3.2 驱动二：差错成本已经被量化得很难反驳

EY 为 Paycom 做的测算（美国样本，2026 更新）<sup>B</sup>：

| 指标 | 数值 |
|---|---|
| 含错的薪资周期比例 | **约 1/5（20%）** |
| 单次差错纠正成本 | **339 美元**（2022 年为 291 美元，涨约 20%） |
| 1,000 人企业年损失上限 | **922,131 美元** |
| 每 1,000 人每年的考勤/工时类差错 | 1,139 次，成本 289,722 美元 |
| 每 1,000 人每年用于纠错的时间 | 单一错类最高 440 小时；前五类合计近 29 个工作周 |
| 平均每周期更正次数 | 15 次 |
| 团队每周期的额外纠错时长 | 41% 的团队需额外 4–10 小时 |
| 全球薪酬准确率均值 | 78% |

**注意这些数字的口径**：这是美国市场、以考勤/工时类差错为主、且由软件厂商委托的测算，**不能直接平移到中国薪酬外包场景**。它的价值不在于绝对值，而在于**结构**：差错成本的大头不是"多付了多少钱"，而是"纠正它消耗的人力与协调成本"。这正好对应核对系统的价值主张——把纠错从"事后跨部门找人"变成"事前一张清单"。

### 3.3 驱动三：交付链条变长，版本成为主要风险源

中国人力资源服务业服务用人单位 5744 万家次<sup>A</sup>，头部外包商在服员工以百万计。当一个变更单要经过"客户提出 → 客户确认 → 一线登记 → 附资料 → 双人核对 → 异常判定 → 出结果 → 归档"八个环节、跨三个异构工具时，出问题的不是算得对不对，而是**交接时没人说得清用的是哪一版**。

这类风险的财务特征是：**损害可见时间滞后**。差错在当期不出声，在客户投诉时才爆。所以它不会被日常管理发现，只会被"事后追责"发现——这是它长期得不到投入的根本原因，也是核对系统存在的理由。

### 3.4 驱动四：员工信任开始进入采购理由

| 指标 | 数值<sup>B</sup> |
|---|---|
| 因持续薪资问题考虑离职的员工 | 53% |
| 出现 2 次薪资错误后开始找新工作的员工 | 50% |
| 认为薪资错误破坏员工与雇主信任的 HR | 91% |

这条驱动在中国市场的强度弱于美国（中国员工对薪资错误的容忍度更高、且离职决策更少由单次薪资差错驱动），**不建议作为主要卖点**，但可作为"客户体验"维度的加分项。

### 3.5 驱动五：知识集中在个人头上

薪酬交付的核心知识是隐性的：为什么这个津贴在这里适用、哪个例外每年 12 月出现、谁该批什么。这些知识不在系统里，在资深专员脑子里。人员在岗时看不出来，人员一走就是产能断崖。

核对系统的隐性价值在于：**把"谁确认过什么"沉淀成可检索的记录**，让知识从人转移到流程。这一条很难量化，但在人员流动率高的外包行业，它是 HR 负责人真正会点头的理由。

### 3.6 被高估的驱动：AI 替代人工

行业报告普遍把"AI 从辅助走向主理"列为第一趋势<sup>B</sup>，AI 部署率在 2026 年已达 47.9%<sup>B</sup>。但具体到薪酬核对：

| 现实 | 数据 |
|---|---|
| 真正在薪酬场景用 AI 的雇主 | **仅 4%**，且不到 10% 有计划<sup>B</sup> |
| 明确表示对薪酬技术不满的组织 | 85%<sup>B</sup> |
| 51% 的企业尚未建立 AI 治理制度<sup>B</sup> | — |
| 61.8% 担忧隐私<sup>B</sup> | — |

**判断**：客户不是不想用 AI，是**不敢让 AI 对钱做决定**。所以任何以"AI 自动核对/自动放行"为卖点的方案，都会在采购的最后一道关被合规或内审否掉。这也直接决定了技术路线（§5）。

## 4. 供给侧：三类玩家与一个夹层空位

### 4.1 三类玩家的分工

| 类别 | 代表 | 主战场 | 对"核对"的处理方式 | 强在哪 | 空在哪 |
|---|---|---|---|---|---|
| **一体化 HR SaaS** | 北森（6000+ 企业 / 2000 万员工）、Moka（2000+ 客户）、用友 BIP、金蝶星瀚、红海云 | 企业内部人事全模块 | 作为算薪模块的一个校验页签，不做跨系统核对 | 客户基数、模块联动、算薪引擎 | 客户的数据在**自己系统内**才成立；一旦跨服务台/文件库就失效 |
| **薪酬专精 SaaS** | 易路（People+ / iBuilder，15 个智能体、40+ 语言）、薪人薪事、智思云 | 复杂算薪、多法人合规 | 强在"算"，弱在"证" | 复杂薪酬规则引擎、全球化合规库 | 不做交付链留痕，因为不算它的责任边界 |
| **综合人力服务商** | 上海外服、中智、FESCO、云生、邦芒、金柚网 | 外包交付本身 | **靠人和 Excel**，双人核对是流程要求不是系统能力 | 客户关系、网点、交付规模 | 恰恰是最痛的一层，但自研动力不足（见 4.3） |
| **全球 payroll** | ADP、CloudPay（130+ 国家）、Alight（180+ 国家）、Papaya、Deel、Remote | 跨国多国薪酬 | 平台内做数据校验与审计报告 | 合规库、集成生态 | 中国本地化交付链（服务台/台账/文件库）不覆盖 |

### 4.2 空位在哪：一张对照表说清楚

| 维度 | 现有玩家的默认假设 | 核对系统的默认假设 |
|---|---|---|
| 数据在哪 | 在我的系统里 | 在**三个互不相通的系统**里 |
| 谁负责正确 | 算法负责 | **人负责，系统只负责让他说清楚** |
| 错了怎么办 | 重算 | **不能重算，只能标记 + 挂出 + 等人工确认** |
| 证据是什么 | 数据库记录 | **原始行 + 版本号 + 确认人 + 时间戳** |
| 审计要求 | 有操作日志 | **日志不可篡改，且能还原完整确认链** |
| 对接方式 | 双向同步 | **只读，不写回** |

最后一行是分水岭。所有 SaaS 厂商的产品逻辑都建立在"我是系统主人"上，所以它们天然倾向做"写回"；而薪酬核对真实场景里，**写回是不可接受的**——一旦系统改动了业务数据，责任归属就说不清了。这个"只读"约束既是产品的护城河，也是大厂不愿意做的原因（只读意味着放弃数据主权带来的锁定效应）。

### 4.3 为什么外包商自己不做

三个现实原因：

1. **试点经济学不成立**：一个批次、40 条样本、4 周、2 名骨干每周 ≤4 小时——这个投入规模撑不起平台化建设，任何重型方案都会在第一周耗尽预算；
2. **责任边界敏感**：审核与质量负责人不代授审批权，系统不能有"自动确认"能力，这限制了产品能自动化到哪一步；
3. **自研没有复用价值**：单客户定制化的核对逻辑无法沉淀为产品，除非先抽象出"字段 + 时间 + 状态 + 留痕"这层通用骨架。

**这正是外部产品的机会**：把通用骨架做出来，把客户特有的字段口径做成配置。

### 4.4 开源侧：组件可复用，整套不存在

按四条技术线检索的结论（核验日期 2026-10-23，详见项目方案 §2）<sup>C</sup>：

| 检索线 | 结论 | 可复用件 |
|---|---|---|
| 薪酬 / HR 域 | 有成熟**算薪**系统，无"变更单核对"层 | `frappe/hrms`（GPL-3.0，注意传染性） |
| 通用对账 | 全部聚焦银行/支付/交易对账，与薪酬域不同构 | `Reconmint`、`reconcileflow`（star <10，仅方法论参照） |
| 审批 / 流程 | 引擎成熟，不应自研 | `Flowable`、`Activiti`、`didi/turbo` |
| 数据质量 | 规则校验可直接复用 | `Great Expectations`、`OPA`（策略即代码） |

**产品含义**：不要试图"找一个开源系统改"，也不要自研工作流引擎。真正要自研的只有三块——**关联键生成、版本有效期判定、审计哈希链**。这三块恰好是别人不愿意做的脏活，也是壁垒所在。

### 4.5 竞争强度判断

| 维度 | 判断 | 依据 |
|---|---|---|
| 直接竞品 | **几乎为零** | 无同构产品；对账类工具不覆盖薪酬版本语义 |
| 替代品威胁 | **高** | Excel + 微信群 + 口头确认，成本为零，且"够用" |
| 上游议价 | 中 | 算薪系统厂商若开放标准校验接口，会削弱独立价值 |
| 客户议价 | **高** | 单客户定制要求多，字段口径各家不同 |
| 新进入者 | 中 | 技术门槛不高，但**数据契约的行业 know-how 门槛高** |

**结论**：这是一个"替代品比竞品更可怕"的市场。产品设计的第一优先级不是功能多，而是**让 Excel 方案显得明显不够用**——这只能靠"一页缺项清单 + 可举证来源位置"这种交付物形态取胜，而不是靠功能清单。

## 5. 技术路线：三条路，只有一条能过合规关

### 5.1 三条路线对比

| | **A · 确定性规则 / 断言式** | **B · 文档 AI（RAG 问答）** | **C · Agent 编排** |
|---|---|---|---|
| 核心能力 | 四类质量断言、版本有效期判定、状态机 | 制度条款问答、变更单与制度比对 | 多步任务自动执行（读表→判定→建单） |
| 准确率特征 | 高（可复算） | 中（受检索质量制约） | 低–中（受步序约束制约） |
| 可解释性 | **完全** | 中（需引用锚定） | 低（黑箱步序） |
| 应对制度变化 | **差**（每变一版改一次规则） | 好（换文档即可） | 好 |
| 合规可接受度 | **高** | 中（须护栏） | **低**（不可自动确认） |
| 实施成本 | 低 | 中 | 高 |
| 适用结论 | 必做（骨架） | 必做（对答层） | 慎做（仅限"准备动作"） |

### 5.2 推荐路线：确定性为骨，LLM 为皮

```
        ┌──────────────────────────────────────────────┐
  输入   │ 只读接入：服务台 / 台账 / 文件库（三源）        │
        └──────────────────┬───────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────┐
  骨架   │ 确定性层（不可由模型替代）                     │
        │  · 关联键生成  PCK-{客户}-{周期}-{类型}-{序号} │
        │  · 版本有效期 + 确认状态 双条件判定            │
        │  · 四类断言：重复编号/空时间/断链/单位差异      │
        │  · 状态机（6 态）· 哈希链审计                  │
        └──────────────────┬───────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────┐
  表皮   │ LLM 层（只做理解与表达，不做判定）             │
        │  · 制度条款检索 + 带引用回答                   │
        │  · 变更单内容与条款的语义比对（产出"疑似"）     │
        └──────────────────┬───────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────┐
  护栏   │ 程序化复核（三道硬闸）                         │
        │  ① 引用可举证：角标必须指向真实 chunk_id       │
        │  ② 数字可溯源：带单位数字逐个回查原文，查不到降级│
        │  ③ 无证据拒答：两路最高原始分不足即拒答，0 token│
        └──────────────────┬───────────────────────────┘
                           ▼
                     一页缺项清单 + 确认链
```

**为什么不能让 LLM 做判定**：薪酬错误的特征是"静默、跨系统、事后暴露"。模型给出一个看起来合理的数字，比给出一个明显的错误更危险——因为它不会被复核者怀疑。所以模型只能做两件事：**把散落文本读成结构化候选**，以及**用自然语言解释已经由程序判定的结果**。

**为什么不能纯规则**：制度每月在变，规则库会腐化。而且真实问法是"我这个外地员工的社保基数调了，上个月的变更单还算数吗"——这种问题规则引擎答不了，必须靠检索 + 表达层。

### 5.3 三条护栏的行业意义

这三条不是工程细节，是**能不能进采购流程的准入条件**：

| 护栏 | 对应客户的哪句话 | 不做的后果 |
|---|---|---|
| 引用可举证 | "每条结果必须给出源位置，否则视为无效输出" | 输出无法被复核，等于又造了一个要人工二次核对的系统 |
| 数字可溯源 | "不得编造最新状态" | 一次编造即触发停止条件，项目终止 |
| 无证据拒答 | "无法确认就进人工队列，不得默认通过" | 默认通过是审计红线，一旦出现即停 |

配套的工程约束（行业通用，非本项目特有）：

- **只读接入**，无写回、无外部消息、无执行接口；
- **双时间戳**（业务发生时间 / 系统接收时间），缺失必须显式标记而非留空；
- **版本有效期**用区间表达，不靠文件名或修改时间猜；
- **审计链路**用哈希链，只追加，数据库层收回 UPDATE/DELETE 权限。

## 6. 商业模式与定价参照

### 6.1 三种模式

| 模式 | 客户 | 收费方式 | 优势 | 劣势 | 适配判断 |
|---|---|---|---|---|---|
| **A · 内部效率工具** | 自用（外包商内部） | 不收费，算成本节约 | 最快落地；无销售成本；可深度定制 | 无外部收入；易被当成 IT 项目砍预算 | ✅ 最适合起步 |
| **B · 对外 SaaS / 私有化** | 中大型企业 HR、财务共享中心 | 按人头/月 或 按年订阅 | 可复制；毛利高 | 实施重、字段口径各异、销售周期长 | ⏸ 第二年再试 |
| **C · 嵌入外包服务** | 外包商的客户 | 计入服务费溢价（+3%–8%） | 与主业绑定，客户不单独决策 | 溢价能力受招标压制 | ✅ 与 A 并行 |

### 6.2 定价锚点（行业参照）

| 参照物 | 价格区间 | 可信度 | 对本产品的含义 |
|---|---|---|---|
| 全球 payroll 平台 | CloudPay 约 $23–31/人/月；Deel $29；Knit $19 | C | 这是"全托管"价格，含算薪+发薪+合规，不能直接对标 |
| 薪酬软件 | $20–180/月基础费 + $4–12/人/月 | C | 核对层通常只能收其 10%–20% |
| 德国 Lohnbüro 外包 | €18–25/人/月 | C | 服务侧成本参照 |
| 财务对账（BlackLine） | 单客户 ARR 可达 100 万美元+ | A | 说明"对账"在超大客户处可卖出高价，但需要极强的审计叙事 |

**定价建议**：

- 内部工具：按"避免的差错成本 + 节省的复核工时 + 审计准备成本"做影子定价，用于立项；
- 对外：**按批次或按变更单量计价**（如 0.5–2 元/条变更单），比按人头更容易被接受——因为价值随变更量线性增长，而与人头数关系弱；
- 溢价路径：把"确认链导出件"做成可对外交付的**合规凭证**，向客户按次收费。这是唯一可能突破工具定价天花板的方向。

## 7. 投入产出：为什么不能拿工时节省做主论证

### 7.1 先算一笔会打脸的账

用项目内基线（**注意：该基线为合成场景虚构样本，仅用于内部前后对比，不得对外引用**）：

```
单客户组年复核工时 = 18 小时/期 × 12 期 = 216 小时 ≈ 0.12 FTE
即使复核效率提升 60%，年节省 = 216 × 60% = 130 小时 ≈ 0.07 FTE
按 25 万元/人年折算 ≈ 3.2 万元/年
```

对照投入：3 人 × 3 个月 = 9 人月 ≈ 27 万元一次性 + 每年运维。**单客户组口径下，纯工时 ROI 为负。**

必须把口径拉到"一个交付中心"才有意义：

```
一个交付中心服务 50 个客户组
  年复核工时 = 216 × 50 = 10,800 小时 ≈ 6 FTE
  效率提升 50% → 节省 3 FTE ≈ 75 万元/年
  投入 27 万元 + 运维 10 万元/年 → 首年回本，次年 ROI ≈ 2.0
```

**结论**：这是一个**规模敏感型**产品。少于 30 个客户组，工时口径算不过账；超过 50 个客户组，账很漂亮。这条结论直接决定销售策略：**必须卖给有集中交付中心的机构，不能卖单点客户。**

### 7.2 真正应该拿来做主论证的三条

| 论证 | 计量方式 | 为什么比工时硬 |
|---|---|---|
| **① 差错暴露时点前移** | 从"客户投诉时发现"前移到"出结果前挂出"。计量：事后投诉数、返工批次数的同比变化 | 一次事后投诉的处理成本（客户关系 + 重发薪 + 可能的赔付）远超全年工具费 |
| **② 举证成本下降** | 一次审计/客户质询的证据准备工时，从"翻邮件找版本"降到"导出确认链" | 这是可承诺的 SLA，能写进合同 |
| **③ 人员流动不带走知识** | 新人独立上手周期、资深人员离岗后的产能恢复时间 | 在人员流动率高的外包行业，这是 HR 负责人真正的痛点 |

三条都不需要虚构基线，都能在试点前后做内部对比，且都能挂到合规/风控预算上。

### 7.3 成本结构（粗估）

| 项 | 量级 | 说明 |
|---|---|---|
| 试点（4 周 / 2 人） | 2 人月 | 范围严格锁定：单批次、40 条样本 |
| 产品化（P1–P5） | 9–12 人月 | 见项目方案 §9 路线图 |
| 年运维 | 2–3 人月 | 制度换版、口径调整、审计校验 |
| 基础设施 | 低 | 单机 Docker Compose 即可；数据量 40–300 条/批，无性能压力 |
| **隐性成本（最易被低估）** | **高** | **字段口径签字、样本脱敏、三方系统导出对齐**——这三件不解决，代码写完也上不了线 |

最后一行值得单独强调：这个项目 70% 的风险不在技术，在**让客户方指定一个对字段口径签字的人**。行业里这类项目最常见的失败方式不是做不出来，而是做出来之后没人认账。

## 8. 风险与合规红线

### 8.1 合规红线（触碰即终止，不是"注意"）

| # | 红线 | 依据 | 后果 |
|---|---|---|---|
| R1 | 薪酬、银行账户、社保记录属**敏感个人信息**，处理须特定目的 + 充分必要 + 严格保护 + **单独同意** | 《个人信息保护法》第 28 条<sup>A</sup> | 民事赔偿 + 行政处罚 + 声誉 |
| R2 | 薪酬文件须**最小知悉**、外发加密，禁止经个人邮箱/网盘传输 | 行业合规指引<sup>C</sup> | 泄露即事故 |
| R3 | 模型/系统**不得拥有确认权**，不得自动放行 | 内控要求 + 项目边界 | 审计否定，项目停止 |
| R4 | 审计记录**只追加**，不可改删 | 内控/审计要求 | 证据链失效，全部结论作废 |
| R5 | 不得写回业务系统、不得对外发消息 | 只读边界 | 责任归属崩塌 |
| R6 | 算法辅助决策须保留**人工复核节点与决策记录**，员工可提异议 | 自动化决策透明度要求<sup>C</sup> | 劳动争议中处于不利地位 |

**R1 的实操含义**：核对系统天然要读全量薪酬数据，这与"最小必要"存在张力。解法是**三层脱敏**：接入层脱敏（姓名/工号替换）、展示层水印、导出层审批 + 用途声明。这三层必须在 P0 阶段就设计进去，不能后补——后补的脱敏一定漏。

### 8.2 商业风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| B1 | 替代品（Excel + 群）足够好用，客户不愿付费 | 🔴 高 | 交付物形态取胜：一页清单 + 来源位置，让 Excel 方案显得明显不够用 |
| B2 | 字段口径无人签字，项目悬空 | 🔴 高 | P0 门禁：无签字不进入开发 |
| B3 | 上游算薪系统开放校验接口，独立价值被吸收 | 🟠 中 | 护城河建在"跨系统版本语义 + 留痕"，不在"校验规则" |
| B4 | 单客户定制化导致无法产品化 | 🟠 中 | 通用骨架 + 配置化字段口径，定制只做配置不做代码 |
| B5 | 监管节奏变化导致卖点失效 | 🟢 低 | 合规是长期收紧趋势，方向确定性强于其他驱动 |
| B6 | 模型幻觉造成错误结论被采信 | 🟠 中 | 三道护栏 + 拒答优先于作答 |

### 8.3 一个容易被忽略的行业性风险

**"核对"这件事的责任主体在客户侧，不在产品侧**。系统只能标记"这单无法确认版本"，不能替客户判断"哪一版是对的"。这意味着：

- 产品无法承诺"零差错"，只能承诺"零默认通过"；
- 销售话术必须从"帮你把差错降到 0"改成"保证每一个不确定都被显式挂出"；
- 一旦对外承诺了前者，第一次出事就是产品责任。

这条边界如果不在立项文件里写清楚，后期一定会演变成验收争议。

## 9. 结论与建议

### 9.1 五条判断（可直接进立项材料）

1. **市场是真的，但不大**。软件口径约 9.5 亿元 TAM，服务成本池约 64 亿元。适合做"高毛利精品"，不适合做"平台叙事"。
2. **时机是真的**。社保入税 + 金税四期把核对从"最佳实践"变成"合规必需"，预算科目从 HR 工具费升级为风控/合规费——这是过去三年最大的变化。
3. **竞争空位是真的**。算薪强的不管核对，做外包的靠人扛，开源侧只有组件。空位在"跨系统版本语义 + 可举证留痕"。
4. **技术路线没有悬念**。确定性为骨、LLM 为皮、三道护栏。任何让模型做判定的方案都会死在合规关。
5. **ROI 要换口径**。工时口径在单客户组算不过账，在交付中心口径才成立；主论证必须换成"暴露时点前移 + 举证成本 + 知识沉淀"，这三条能挂合规预算。

### 9.2 分阶段建议

| 阶段 | 时间 | 目标 | 关键动作 | 通过标准 |
|---|---|---|---|---|
| **P0 论证** | 3 天 | 拿到签字 | 字段字典 + 口径签字单；三类清单定稿；40 条样本脱敏方案 | 有签字人，否则不启动 |
| **P1 试点** | 4 周 | 证明能跑通 | 只读接入、关联键、四类断言、一页清单 | 40/40 差异可定位到来源 |
| **P2 沉淀** | 2–3 月 | 抽象出骨架 | 把"字段+时间+状态+留痕"做成配置层，客户差异全部配置化 | 第二个客户组接入 ≤2 周 |
| **P3 复制** | 6–12 月 | 验证规模经济学 | 铺到 30–50 个客户组，验证 7.1 的规模拐点 | 单中心 ROI > 1.5 |
| **P4 外化** | 12 月+ | 试水对外 | 私有化交付给 2–3 家外部客户，验证定价 | 至少 1 家愿意为"确认链导出件"付溢价 |

**关键提醒**：P1 到 P2 是最容易失败的一跳。试点做出来的东西一定带满客户特有逻辑，如果 P2 不做抽象就直接复制，第二个客户会推翻第一个客户的实现。**P2 的验收标准应该是"第二个客户接入工时 ≤ 第一个客户的 1/3"，而不是"功能更多"。**

### 9.3 三个必须先回答的问题

在写第一行代码之前，这三件事没有答案就不该开工：

| # | 问题 | 谁回答 | 为什么致命 |
|---|---|---|---|
| Q1 | **谁对字段口径签字？** | 业务负责人 | 没有签字人，验收就没有依据，做完也不认账 |
| Q2 | **目标客群的规模拐点在哪？** | 业务负责人 + 财务 | 少于 30 个客户组算不过账，销售策略必须据此定 |
| Q3 | **"零默认通过"能不能写进对外承诺？** | 质量负责人 + 法务 | 能写就是核心卖点；不能写就要重新设计价值主张 |

### C. 名词表

| 术语 | 含义 |
|---|---|
| **核对层（Reconciliation Layer）** | 在算薪与交付之上，负责证明"结果依据哪一版本、谁确认"的独立能力层 |
| **关联键（Mapping Key）** | 跨三源拼接变更单的统一编号，如 `PCK-{客户}-{周期}-{类型}-{序号}` |
| **双时间戳** | 业务发生时间（客户何时提出）与系统接收时间（系统何时收到），二者不可合并 |
| **版本有效期** | 用 `valid_from` / `valid_to` 区间表达版本有效范围，不靠文件名或修改时间推断 |
| **确认链** | 从"谁查过 → 用哪版 → 提什么建议 → 谁确认"的完整可还原序列 |
| **哈希链审计** | 每条审计事件携带前序哈希，任何删改都会导致链断裂，可离线校验 |
| **零默认通过** | 无法确认版本或关键字段的单据 100% 进入人工队列，系统永不自动放行 |
