## 1. 结论先行

### 1.1 三条核心判断

| # | 判断 | 依据 | 对方案的影响 |
|---|---|---|---|
| 1 | **GitHub 上不存在可直接使用的"薪酬服务变更核对系统"** | 全网检索 payroll / reconciliation / 审批 / 审计四条线，均无同构项目（见 §2） | 放弃"找现成系统改造"，改为**组合成熟开源组件 + 自研核对与追溯层** |
| 2 | **瓶颈不是自动化不足，而是交接点的版本追溯与确认留痕** | f01 业务负责人明确"先观察每个交接点，而不是直接增加自动化"；f10/f11 一线版本对不上；f23/f24 交接需列明版本与确认状态 | 一期**不做 OCR、不做自动审批、不做金额计算建议**，只做"看清楚 + 留得住痕" |
| 3 | **"只读"不是保守，而是验收前提** | f32 仅开放脱敏只读导出；f44 无法确认即进人工队列；f41 正式结论须授权人员确认 | 系统**无写回、无外部消息、无执行接口**；所有动作止于"标记 + 建议 + 人工确认" |

### 1.2 一句话方案

> 在单批次薪酬变更单范围内，建设一个**只读接入、双时间戳、版本有效期 + 确认状态双条件判定、全链路哈希链审计**的核对工作台，用一页"缺项清单"替代泛化摘要，把 40 条脱敏样本的金额差异全部定位到来源，并在试点结束时交出可复核的确认链。

### 1.3 不做什么（与做什么同等重要）

| 明确排除 | 原因 |
|---|---|
| 计算真实员工薪资 / 生成工资表 | f05、f52 试点边界 |
| 自动付款、提交税务申报 | f52 本轮协作边界 |
| 模型审批、自动放行 | f22 模型无审批权限；f44 不默认通过 |
| 覆盖原值、静默重试、编造最新状态 | f14、f35 |
| 写回业务系统 / 对外发消息 | f32 接口边界 |
| 全量铺开、多客户并行 | f05 仅一个批次；唐映秋两次追问范围未定 |

## 2. GitHub 开源项目调研

### 2.1 检索方法与结论

按四条技术线分别检索 GitHub（按 star 排序，核验日期 2026-10-23）：

| 检索线 | 关键词 | 结果规模 | 结论 |
|---|---|---|---|
| 薪酬 / HR 域 | `payroll`、`hrms`、`payroll engine` | 55,881 个仓库 | 有成熟的**薪酬计算**系统，但**没有"变更单核对"**这一层 |
| 通用对账 | `reconciliation`、`reconciliation audit trail` | 星标最高仅个位数到两位数 | 全部聚焦**银行/支付/交易对账**，与"薪酬变更单版本核对"不同构 |
| 审批 / 流程 | `bpmn workflow engine` | 万星级多个 | 审批引擎成熟，**不应自研** |
| 数据质量 | `great_expectations`、`data quality validation` | 万星级 | 规则校验可复用，正好对应 f33 的四类检查 |

**结论**：`reconciliation` 类项目（Reconmint、reconcileflow、TradeRecon 等，star 均 < 10）在**方法论上高度同构**——"确定性验证 + 类型化差异 + 可重放决策 + 审计链"，但**代码不可直接复用**。真正可复用的是**组件**，不是整套系统。

### 2.3 选型评审

| 方案 | 描述 | 优点 | 致命问题 | 结论 |
|---|---|---|---|---|
| A. 直接 Fork frappe/hrms | 在 HRMS 上二次开发变更单模块 | 薪酬域完整，开箱即有员工/薪资结构 | GPL-3.0 传染性；HRMS 是**计算系统**不是**核对系统**，改造量≈新建；引入大量无关模块（招聘、考勤、绩效） | ❌ 否决 |
| B. 用 Flowable 编排全流程 | 把"客户确认→登记→双人核对→出结果"画成 BPMN | 审批语义标准，留痕天然 | 试点仅 4 周 / 2 人 / 每周 ≤4h (f03)，BPMN 建模与运维成本远超收益；且 f23 要求的"交接列明版本与未结项"是**数据字段要求**，不是流程节点需求 | ⏸ 二期再议 |
| C. Reconmint / reconcileflow 二次开发 | 复用对账引擎 | 方法论一致 | star < 10，无社区、无测试、无协议保障，生产不可用 | ❌ 否决 |
| D. **自研核对层 + OPA + GE 规则 + PostgreSQL** | 轻量技术栈，只做核对与追溯 | 4 周可交付；只读边界天然；审计链可控；中文/合规自持 | 需要自己写版本判定与状态机（但状态仅 6 个，工作量可控） | ✅ **推荐** |

**推荐理由**：试点约束（f03：四周、两名骨干、每周不超四小时）决定了**任何重型平台化方案都会在第一周耗尽预算**。而 REQ-1~REQ-6 的技术本质是"**字段 + 时间 + 状态 + 留痕**"，用一个 PostgreSQL + FastAPI + 确定性状态机即可完整覆盖，无需 BPMN。

## 3. 技术选型对比与推荐架构

### 3.1 技术栈

| 层 | 选型 | 理由 | 对应事实 |
|---|---|---|---|
| 前端 | Next.js 15 + TypeScript + Tailwind CSS | 一页式缺项清单 + 交接看板；SSR 便于内网部署 | f15 要"一页缺项清单"，不要长摘要 |
| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2.0 | 与数字化侧数据分析同栈（pandas/polars 做拼接与质量检查） | f30/f31/f33 |
| 数据库 | PostgreSQL 16 | 部分唯一索引表达"版本有效期"；`tstzrange` 做区间判定；触发器写审计 | f24/f34 |
| 策略引擎 | OPA（Rego） | 越权拦截规则可单测、可版本化，不散落在业务代码 | f41/f44 |
| 质量校验 | 自研 SQL 断言 + Great Expectations（可选） | f33 四类检查确定性实现即可，GE 仅在二期扩展 | f33 |
| 审计 | 应用层哈希链（SHA-256 前序哈希）+ 只追加表 | 满足"谁查过/用哪个版本/提什么建议/谁确认"(f45)，且可离线校验完整性 | f45/f43 |
| 部署 | Docker Compose（内网单机） | 试点环境最小化；无云依赖，符合"只读 + 脱敏"边界 | f32 |

```

└───────────────────────────┬──────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  核对层（Reconciliation Core）                                │
│  · 关联键映射表  · 版本有效期判定  · 确认状态机                │
│  · 双时间戳比对  · 四类质量断言  · 未匹配行挂出                │
└───────────────────────────┬──────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────────┐
│ 交接看板      │   │ 人工核对队列  │   │ 审计链（哈希）    │
```

### 3.3 关键架构决策记录（ADR）

| ID | 决策 | 备选 | 理由 | 后果 |
|---|---|---|---|---|
| ADR-01 | 不做写回，仅只读 | 双向同步 | f32 明确写回/外部消息/执行接口均不开放 | 无法自动修复数据；所有修正走人工 |
| ADR-02 | 版本判定用"有效期 + 状态"双条件 | 文件名 / 修改时间 | f24 明确"不靠文件名猜最新版本" | 需维护 `valid_from/valid_to`，导入时必须给值 |
| ADR-03 | 双时间戳（业务发生 / 系统接收） | 单时间戳 | f34 明确双记录；f13 回填时间 ≠ 发生时间 | 每个来源必须能提供发生时间，否则标"缺失" |
| ADR-04 | 读取失败保留快照 + 标时间 | 重试 / 补写 | f35 不得编造状态、不得悄悄重试业务动作 | 前端必须显著呈现"数据停留于某时刻" |
| ADR-05 | 审计用哈希链，不用普通日志表 | 普通 append 日志 | f45 需还原完整确认链；哈希链可证明未被删改 | 写入成本略增，可接受（样本量 40~300） |
| ADR-06 | 状态机自研（6 态） | BPMN 引擎 | 试点 4 周约束；状态语义简单且强确定性 | 二期若引入多级审批需迁移（已预留 `approval_matrix`） |

## 4. 业务流程拆解：现状 → 失败方式 → 系统边界

### 4.1 现状泳道（8 步 + 3 交接点 + 4 类异常）

| 步 | 环节 | 执行角色 | 输入 | 输出 | 交接点 | 已知失败方式 |
|---|---|---|---|---|---|---|
| 1 | 客户提出变更 | 客户经理（叶书线） | 客户邮件/群消息 | 变更诉求 | **H1** 客户→服务台 | 截止后补发（f11）；群消息先行（f13） |
| 2 | 客户确认 | 客户协同 | 变更诉求 | 客户书面确认 | **H1** | 时效压力导致跳过二次确认（f50） |
| 3 | 变更登记 | 一线专员（林亦舟） | 确认件 | 变更单初稿（草稿） | — | 草稿引用旧金额（f11） |
| 4 | 附资料 | 一线专员 | 原始版本 | 证据附件 | — | 邮件与月度表版本对不上（f10） |
| 5 | 双人核对 | 一线专员 + 复核 | 草稿 + 原始版本 | 核对结论 | **H2** 登记→核对 | 版本追溯失败；责任归属扯皮 |
| 6 | 异常判定 | 复核 | 核对结论 | 异常标记 / 正常 | — | 截止后更正未单独标出（f11） |
| 7 | 出具结果 | 业务负责人（顾明岚线） | 核对结论 | 正式结果 | **H3** 核对→出结果 | 未确认项被归到对方名下（f25） |
| 8 | 归档与审计 | 资料负责人 | 全链记录 | 确认链 | — | 只留最终摘要（f45） |

### 4.2 失败方式 → 系统边界

| 失败方式 | 发生环节 | 损害可见时间 | 可拦截？ | 系统应对 | 需人工接收人 |
|---|---|---|---|---|---|
| 引用旧金额草稿出结果 | 5→7 | **事后**（客户投诉） | 部分（需版本比对） | 版本断链即拦截，进人工队列 | 复核（傅景口径）+ 业务负责人 |
| 群消息先行、回填时间失真 | 1→3 | 事后 | 是 | 双时间戳 + 发生时间缺失标记 | 一线专员补录并签字 |
| 拼接错行（无统一编号） | 3→5 | **静默** | 是 | 未匹配行单独挂出，禁止默认合并 | 数字化工程师（秦芮） |
| 读取失败用旧值 | 任意 | 静默 | 是 | 快照 + 时间标记 + 人工核查提示 | 秦芮 + 当班人员 |
| 越权访问跨企业资料 | 2/7 | 事后 | 是（事前） | OPA 拦截 + 审计记录 | 审核（傅景） |
| 未确认项挂到接收方 | 7 | 事后（责任争议） | 是 | 责任字段不可跨主体转移，必须原责任人 + 截止时间 | 流程协调（唐映秋） |

### 4.3 系统边界图（谁做什么）

```
                ┌──────────── 系统可做（确定性） ────────────┐
客户确认 ──→ 变更登记 ──→ 双人核对 ──→ 出具结果
                │            │              │
                │            └── ❌ 不可做：代替人工判断"哪版是对的"
                └── ❌ 不可做：自动补填发生时间、自动合并拼接行
                                        └── ❌ 不可做：自动确认、自动付款、自动报税
```

**判定原则**：只有**可复算、可回放、可对照原始行**的动作进入系统；任何需要"业务意图解释"的动作一律留在人工队列。

## 5. 需求到功能的映射（REQ-1 ~ REQ-6）

| 需求 | 优先级 | 功能模块 | 关键交互 | 验收判据 | 负责人（待确认） |
|---|---|---|---|---|---|
| **REQ-1** 交接点版本追溯 | P0 | 交接看板（Handoff Board） | 交接单固定三栏：**最新版本 / 未确认事项 / 截止时间**；不能只发"已处理" | 版本断链数与未结项数可统计；每条交接可追到版本 ID | 唐映秋（规则）/ 傅景（可追溯性） |
| **REQ-2** 统一关联键与字段口径 | P0 | 映射键 + 字段字典 | 自动生成 `PCK-{客户编号}-{薪资周期}-{变更类型}-{序号}`；未匹配行独立挂出 | 40 条样本拼接成功率；未匹配行 100% 单独挂出且经人工确认 | 秦芮 + 字段口径签字人（待确认） |
| **REQ-3** 双时间戳与快照 | P1 | 时间轴 + 快照标记 | 同屏并列"业务发生时间 / 系统接收时间 / 快照时间"；过期单高亮挂出 | 过期单可被正确挂出；快照缺失时显式提示"停留于某时刻" | 秦芮 |
| **REQ-4** 必审 / 授权 / 越权三类清单 | P0 | 审批矩阵 + OPA 闸门 | 三类清单以配置表呈现，可导出签字版 | 无法确认版本的单据 **100% 进人工队列，0 默认通过** | 傅景 会同 顾明岚 |
| **REQ-5** 全过程审计留痕 | P1 | 审计链视图 | 一次确认链可按时间轴还原：谁查过→用哪版→提什么建议→谁确认 | 抽查 5 条样本可完整还原；链完整性校验通过 | 傅景 + 资料责任人（待确认） |
| **REQ-6** 时效与复核窗口冲突 | P2 | 口径对齐页（不建工具） | 只呈现"工时/返工次数/确认完整率"三项指标，不做优先级裁决 | 三项指标同时出数，不以单一工时解释效果 | 叶书 + 顾明岚 |

### 5.1 一页缺项清单（核心界面形态）

## 6. 数据模型与关键判定规则

### 6.1 核心表

```sql
-- 1. 变更单主表（一个逻辑变更单）
CREATE TABLE change_request (
  cr_id            TEXT PRIMARY KEY,              -- PCK-客户编号-薪资周期-类型-序号
  client_code      TEXT NOT NULL,
  pay_period       TEXT NOT NULL,                 -- 2026-10
  change_type      TEXT NOT NULL,
  source_tool      TEXT NOT NULL,                 -- service_desk / ledger / file_library
  matched_by       TEXT NOT NULL,                 -- auto / manual（拼接方式，f30）
  matched_rule_id  TEXT,                          -- 映射规则版本，f31
  status           TEXT NOT NULL DEFAULT 'draft', -- 见 6.3 状态机
  created_at       TIMESTAMPTZ NOT NULL
);

-- 2. 版本表（版本有效期，f24；过期不得覆盖已确认，f34）
CREATE TABLE change_version (
  version_id    TEXT PRIMARY KEY,
  cr_id         TEXT NOT NULL REFERENCES change_request(cr_id),
  version_no    INT  NOT NULL,
  amount        NUMERIC(14,2),
  currency      TEXT,
  valid_from    TIMESTAMPTZ NOT NULL,
  valid_to      TIMESTAMPTZ,                       -- NULL = 当前有效
  confirm_state TEXT NOT NULL,                     -- draft / confirmed / void
  confirm_by    TEXT,                              -- 授权确认人（f41）
  void_reason   TEXT,                              -- 作废必留原因（f24）
  received_at   TIMESTAMPTZ NOT NULL               -- 系统接收时间（f34）
);
-- 同一变更单同一时刻只能有一个有效版本
CREATE UNIQUE INDEX ux_version_active
  ON change_version (cr_id) WHERE valid_to IS NULL AND confirm_state <> 'void';

-- 3. 双时间戳（f13、f34）
CREATE TABLE occurrence (
  occurrence_id  BIGSERIAL PRIMARY KEY,
  cr_id          TEXT NOT NULL,
  occurred_at    TIMESTAMPTZ,                      -- 业务发生时间，可为 NULL（必须显式标记缺失）
  occurred_src   TEXT,                             -- mail / group_msg / ledger（来源证明）
  occurred_missing BOOLEAN NOT NULL DEFAULT FALSE, -- 缺失值 ≠ 未确认值（f31）
  received_at    TIMESTAMPTZ NOT NULL,
  is_late_backfill BOOLEAN NOT NULL DEFAULT FALSE  -- 群消息先行、表格后补（f13）
);

-- 4. 交接记录（f20、f23、f25）
CREATE TABLE handoff (
  handoff_id   BIGSERIAL PRIMARY KEY,
  cr_id        TEXT NOT NULL,
  version_id   TEXT NOT NULL,
  from_role    TEXT NOT NULL,
  to_role      TEXT NOT NULL,
  receiver     TEXT NOT NULL,                      -- 接收人签字
  open_items   JSONB NOT NULL,                     -- 未结项（结构化，不可为空数组）
  due_at       TIMESTAMPTZ NOT NULL,               -- 截止时间（必填）
  owner_of_open_items TEXT NOT NULL,               -- 未确认项归属原责任人（f25）
  handed_at    TIMESTAMPTZ NOT NULL
);

-- 5. 人工核对队列（f44：不得默认通过）
CREATE TABLE review_task (
  task_id     BIGSERIAL PRIMARY KEY,
  cr_id       TEXT NOT NULL,
  reason_code TEXT NOT NULL,   -- version_broken / key_field_missing / amount_diff / unauthorized
  blocked     BOOLEAN NOT NULL DEFAULT TRUE,       -- TRUE = 禁止出结果
  assigned_to TEXT,
  decision    TEXT,            -- confirm / reject / escalate（仅人工可写）
  decided_by  TEXT,
  decided_at  TIMESTAMPTZ,
  evidence    JSONB            -- 复核记录（f42 每条结果须关联）
);

-- 6. 审计事件（哈希链，f45）
CREATE TABLE audit_event (
  seq        BIGSERIAL PRIMARY KEY,
  event_type TEXT NOT NULL,   -- view / export / propose / confirm / void / deny
  actor      TEXT NOT NULL,
  cr_id      TEXT,
  version_id TEXT,
  payload    JSONB NOT NULL,
  prev_hash  TEXT NOT NULL,
  hash       TEXT NOT NULL,   -- sha256(prev_hash || canonical(payload))
  at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 6.2 四类质量断言（f33）

| 检查 | 规则 | 处理 | 依据 |
|---|---|---|---|
| 重复编号 | `GROUP BY cr_id HAVING count(*)>1` | 全部标记，**不自动去重**，保留原行 | f33 |
| 空时间 | `occurred_at IS NULL OR received_at IS NULL` | 标 `occurred_missing`，进缺项清单 | f33 |
| 版本断链 | 版本号不连续 / `valid_to` 与下一版 `valid_from` 不衔接 | 进人工队列，禁止出结果 | f33、f44 |
| 单位差异 | `currency` 不一致或金额量级偏离 100 倍 | 挂出，需人工确认单位 | f33 |

> 原则：**问题记录必须保留原行**（f33）。系统只做"标记"，不做"清洗后沉默"。

### 6.3 状态机（6 态，强确定性）

```
draft ──登记完成──→ pending_dual_check ──双人核对通过──→ confirmed
  │                        │                                  │
  │                        └──发现异常──→ manual_queue ──人工决策──→ confirmed
  │                                            │
  └──作废(留原因)──→ void ←──────────────────────┘（拒绝）

confirmed ──出具结果（人工）──→ issued
任何状态 ──关键字段无法确认──→ blocked（暂停试点触发条件之一）
```

**不可逆动作前的确定性校验**（进入 `confirmed` 之前必须全绿）：

| 校验 | 不通过时 |
|---|---|
| `version_no` 连续且仅一个有效版本 | 进 `manual_queue`，`blocked=TRUE` |
| `confirm_by` 属于授权角色 | OPA 拒绝，记 `deny` 审计事件 |
| `occurred_at` 已确认（或有明确"缺失"标记 + 签字） | 进缺项清单 |
| 金额差异有来源定位 | 禁止 `issued` |

## 7. 审计留痕与权限边界设计

### 7.1 审计四问（f45）

| 问题 | 记录方式 | 载体 |
|---|---|---|
| 谁查过 | 每次 `view` / `export` 写 `audit_event`（含 IP、角色、查询条件） | `audit_event` |
| 用哪个版本 | `version_id` + `version_no` + `received_at` 三元组 | `audit_event.version_id` |
| 提了什么建议 | 系统建议以 `propose` 事件独立记录，**永不覆盖原值**（f14） | `audit_event.payload.suggestion` |
| 谁确认 | `confirm` 事件 + `change_version.confirm_by` 双写 | 两处一致才算有效 |

**硬约束**：
- 审计记录**只追加**，无 UPDATE / DELETE 权限（数据库层面收回）；
- 每次导出必须写 `export` 事件，包含导出行数与用途声明；
- 哈希链每日校验一次，断链即触发停止条件（§8.4）。

### 7.2 三类清单（REQ-4）

#### 清单 A · 必审操作

| # | 操作 | 触发条件 | 必审角色 | 是否阻断出结果 |
|---|---|---|---|---|
| A1 | 变更单正式确认 | 任意金额变更 | 对应业务负责人 | 是 |
| A2 | 版本作废 | 版本冲突 | 流程协调 + 业务负责人 | 是 |
| A3 | 截止后补发处理 | `received_at > due_at` | 复核 | 是 |
| A4 | 未匹配行手工合并 | 拼接失败 | 数字化工程师 | 是 |
| A5 | 结果对外使用 | 出结果后 | 客户协同代表（f04） | 是 |

#### 清单 B · 授权角色

| 角色 | 可提交 | 可确认 | 可导出 | 可改口径 | 可停止试点 |
|---|---|---|---|---|---|
| 一线服务专员 | ✅ | ❌ | 受限（脱敏） | ❌ | ❌ |
| 流程协调员 | ✅ | ❌ | 受限 | ❌ | ❌ |
| 数字化工程师 | ❌ | ❌ | 受限 | 提议 | ❌ |
| 审核与质量负责人 | ❌ | ❌（不代授审批权，f41） | ✅ | 质量口径 | ✅（f04） |
| 业务负责人 | ✅ | ✅ | ✅ | 业务口径 | ✅（决定范围，f04） |
| 客户协同代表 | ❌ | ❌ | 受限 | 用途确认 | ❌ |

#### 清单 C · 越权拦截

| # | 场景 | 拦截点 | 规则（OPA） | 记录 |
|---|---|---|---|---|
| C1 | 跨企业资料访问 | API 网关 | `input.client_code ∈ actor.authorized_clients` | `deny` 事件 |
| C2 | 非授权角色确认 | 状态机 | `actor.role == "business_owner"` 且 `actor ∈ cr.owner_whitelist` | `deny` 事件 |
| C3 | 模型/系统自动确认 | 应用层 | 无自动化 principal 可写 `confirm` | `deny` 事件 |
| C4 | 未脱敏导出 | 导出服务 | `export.scope == "desensitized"` 否则拒绝 | `deny` 事件 |
| C5 | 审计日志查阅越权 | 审计查询 | `actor.role ∈ ["auditor","business_owner"]` | `deny` 事件 |

> 三类清单须在试点前**定稿并签字**（f44 下一步验证）。定稿人：业务负责人（顾明岚）决策、审核与质量负责人（傅景）提供质量口径。
