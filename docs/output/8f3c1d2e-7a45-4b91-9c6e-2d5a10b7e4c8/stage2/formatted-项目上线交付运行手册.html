一、文档说明

本章交代手册的用途、读者与术语口径，是后面所有操作步骤的前提。

1.1 编制目的

本手册解决一个问题：系统从项目组交到运维和业务运营手里之后，在没有原开发人员的情况下，如何让它稳定跑起来、坏了怎么修、谁能动它、动完留什么痕。

二、系统交付概述

先建立整体印象：交给运维的是什么、它不做什么、当前哪些能力还没补齐。

2.1 系统定位

系统的核心风险不是"查不到制度"，而是答得像制度、其实不在制度里。因此本期交付的能力围绕三件事构建：答案必须能回到原文、数字不由模型产出、没有依据就闭嘴。

能力边界同样是交付内容的一部分。运维需要清楚哪些事系统永远不会做：

系统不做表现
不写回业务系统没有回写接口，建单止于草稿加人工确认
不自动审批、不自动放行L3/L4 分级不给凭证，模型拿不到凭证就建不了单
不编造最新状态读取失败保留快照并标注"停留于某时刻"，不重试业务动作
不做真实薪资计算与发放无工资表生成、无付款、无报税动作
不对外发消息无消息推送通道，转人工只记录不触达外部

任何要求系统"自动修数据""自动确认""直接对外发结果"的需求，都属于越界需求。运维应按变更管理流程拒绝，而不是临时变通。

2.3 运行架构

系统是四层单向依赖结构，运维排障时可以按层定位问题：

分层结构

入口层 CLI（main.py） / HTTP（FastAPI：/chat SSE、/admin、/api/v1）

|

编排层 orchestrator：检索 -> 组装 prompt -> 生成 -> 护栏 -> 引用

|

+----------+----------+

检索层 hybrid（向量 + BM25 + RRF） | llm 适配层（唯一出网口） | guard（程序化复核）

|

持久层 store/db.py -> store/chat_repo.py（只有这里写 SQL）

排障时这条依赖顺序就是排查顺序：入口层报错先看协议与鉴权，编排层报错看检索与模型，持久层报错看库与锁。唯一出网口是 core/llm/http.py，所以"是否真的调了模型"只要看这一个地方的日志就能确定。

2.5 关键约束

以下四条是当前实现的客观限制，不是配置项，不能靠调参绕过：

  1. 索引重建与提示词缓存是单实例语义。多实例部署时，重建锁与缓存失效不跨进程，会出现"一台已用新制度、一台还在用旧制度"。要做多实例，必须先把这两件事挪到外部队列或共享存储。
  2. 限流是进程内滑动窗口。对外 /api/v1 多实例时实际上限等于实例数乘以配额。
  3. 网页端 JWT 路径当前没有限流（见 2.6 缺口 G-03）。在补齐之前，不得把员工入口直接暴露到公网。
  4. BM25 是内存倒排。千条切片内无感，上万条需要换 tsvector 或独立检索服务。

  阈值硬提醒：MIN_VECTOR_SCORE 与 MIN_BM25_SCORE 的当前值是按 hash 占位向量标定的（有效问题 0.27~0.38，越界问题不超过 0.12）。换成 bge-m3 这类真实向量模型后相关分会整体抬高，不重标定就会出现大范围误拒答。这类故障的典型表现是"系统突然什么都不知道了"，而日志里没有任何错误。

3.6 上线门禁

上线评审按下列四条执行，任一条不满足则不上线：

  1. 25 项检查中所有【阻塞】项通过；未通过项须技术负责人加业务方共同签字接受。
  2. 上线前 24 小时冻结代码与提示词，只接受修复阻塞项的热修。
  3. 上线后 2 小时双人值守，盯四个指标：错误率、首字延迟 P95、LLM 429 比例、注入拦截次数。
  4. 首日抽样 20 条真实问答加 5 张真实单据人工复核，准确率低于 95% 即启动回滚评估。

四、系统初始化配置

系统起来之后，把制度、参数、账号与对外凭证配到位。

4.1 制度入库

两条路径：命令行 build（首次全量）与后台「知识库」页上传（日常增量）。

后台路径为：知识库页，选文件，填标题、版本、生效期，上传。约束如下：

  • 支持 .md / .txt / .pdf，单文件不超过 10 MB；
  • 上传后不会立刻生效，触发后台重建，页面顶部显示"重建中"；
  • 重建期间员工照常提问，用的是上一版索引；完成后原子热切换；
  • 同一 doc_id 已存在时被拒绝（KB_003），制度不能静默覆盖。

  PDF 的边界必须说清：只支持有文本层的 PDF，扫描件直接报错并提示需要 OCR。这是刻意设计——静默产出一份空文档比报错糟糕得多：上传成功、问答永远答不出，还找不到原因。表格多的制度建议用 Markdown，pypdf 只给文本流，行列关系会丢。

4.2 制度参数与员工档案

初始化命令

payroll-check data seed # 16 个参数 + 5 份档案（含一个缺法人归属的样本，用于验证阻断）

payroll-check data params # 核对参数与条款出处

数值只从 policy_params 来，每一行都必须有 source_clause。参数缺失时系统返回 missing，这是给 Agent 的行动信号：必须转人工，不许猜。地区优先级为"本地区，其次全国默认，最后 missing"。

当前只有 310000 一套参数，其他地区会全部 missing。这是刻意行为，不是缺陷。

4.3 部门与组织归属

组织命令

payroll-check dept add --name 华东区域 --code EC

payroll-check dept add --name SSC上海 --parent 华东区域

payroll-check dept assign --username zhangsan --dept SSC上海 --title 高级薪酬专员

payroll-check dept list

只做两级是有意的：SSC 要回答的是"华东区这个月多少人在问冻结期、拒答率多少"，两级够用；更深的组织树属 HR 主数据，应对接而非自建。

统计口径必须看清，否则数字会被误读：

项口径
提问数次数，一人问 10 次算 10 次
参与人数该组有提问的不同账号数
拒答率refused / (answered + partial + refused)，排除流式占位行
时间窗固定近 30 天
未归属未挂部门或部门已删的问答合成一组

4.4 对外 API Key

Key 命令

payroll-check apikey add --name hr-portal --owner 张工 --rate-limit 60

payroll-check apikey list

payroll-check apikey revoke --id 3f2a1b0c # 支持短 id

明文只打印一次，库里只存 sha256。丢了就吊销重发，不要试图找回。Key 无过期时间，只有"吊销"，定期轮换要靠人——建议写进运维日历，按季度轮换一次。

4.5 Agent 开关

变量作用
AGENT_ENABLED能力是否可用（关掉后 Agent 模式不可选）
AGENT_DEFAULT_MODE/chat 默认走 rag（固定检索）还是 agent（工具链）

上线初期建议 AGENT_DEFAULT_MODE=rag，观察两周后再切换默认值。Agent 模式的最终答案不是真流式：工具循环跑完后一次性发 delta，前端用打字机弥补观感，对超长对话的首字延迟影响明显。

5.4 制度换版与回滚

这是本期最重要的运行变化。旧做法是"先删旧版再传新版"，两步之间索引里没有这份制度，员工提问会直接拒答；真实制度每年都改，这个窗口期就是事故窗口。

正确做法：知识库页，上传，保持 doc_id 不变、版本号加一，上传。系统在同一事务内完成：新版入库（active）、旧版置 superseded、触发重建，全程没有"制度不见了"的时刻。

状态含义问答是否使用
active现行版本是（且生效日已到）
superseded被新版替代，留档否
deleted软删，文件保留否

三条硬规矩：

  1. 同 doc_id 加同版本重复上传会被拒绝（KB_003）。要改内容就提升版本号，否则"当时生效的是哪一版"说不清。
  2. 版本号是数字，不做大小比较。系统只用它判断"是不是同一版"。展示用版本串（v1.0、2026-A）填在「版本标识」里，与纸质文件对照。
  3. 待生效版本不进索引。effective_from 填未来日期时，这一版入库但不进索引，列表页显示「待生效」徽标。

回滚：文档详情，版本历史，点「回滚到本版」。回滚不是删除：把旧版重新置 active，当前版变 superseded，再重建索引。新版写错了用回滚，不要用删除——删掉会让制度整体消失，回滚则全程有依据。

5.5 索引重建

全量重建是唯一方式（FAISS 索引无法局部摘除向量），但只有内容变化的切片才重新向量化，向量缓存在 data/index/vec_cache_*。

场景动作预计影响
制度上传、换版、回滚后台自动触发重建期间用旧索引，无服务中断
换向量模型必须手动重建（build）重建期间不可检索旧索引，需安排窗口
索引损坏删除 data/index/ 后 build全量重建，耗时与切片数成正比

重建失败不影响线上检索——重建失败时旧索引仍在使用，但必须当天处理，否则下一次换版就没有退路。

5.6 提示词变更

提示词页，编辑，点「用草稿预览」，保存。三条约束：

  1. 保存等于新建版本，历史永远在，可回滚到任意版本；
  2. {context} 与 {question} 两个占位符必须保留，否则拒绝保存——少了 {context} 模型只拿到问题、没有资料，它会直接开始编，而事故发生在员工页；
  3. 页面上的「系统强制追加」改不了：角标格式是系统契约不是话术，护栏按 [1] [2] 核对引用，模型不标角标答案就会被判"引用缺失"。

生效时机：保存后下一个问题就用新版（单 worker 立即生效；多 worker 最长等 PROMPT_CACHE_SECONDS）。每条回答都记下当时用的 prompt_version，审计页可查。

  流程要求：提示词改动属高风险变更，须走 10.3 的评审清单，且改动后必须重跑注入红队用例。提示词调优会悄悄削弱拒绝倾向，这是最容易回归的地方。

7.3 常见故障场景

以下是试点期最可能遇到的八类故障，按发生概率排序。每类都给出定位顺序与处置动作。

场景 1：服务起不来

先看启动日志首屏。三类原因：端口占用（8000）、data/.auth_secret 不可写、迁移失败。迁移在一个事务内，失败会整体回滚，不会留半张表——回滚后可安全重试，但重试前必须先备份。

场景 2：全部问题都拒答，且无报错

这是最容易被误判为"模型坏了"的故障，最常见原因是闸门阈值与向量模型不匹配（见 3.4）。排查顺序：

  1. payroll-check info 看 manifest 的 backend 与 dim 是否与当前配置一致；
  2. 若不一致，重建索引；
  3. 若一致，用 --debug 跑一个已知有效问题，看两路 best_vector_score、best_bm25_score 与阈值的关系；
  4. 分数整体低于阈值，说明换模型后未重标定，需重新标定而非下调阈值凑数。

场景 3：全站答不出来，日志里有大量 429

预算或并发配额耗尽，这是"预算烧完"的典型表现。立即：AGENT_DEFAULT_MODE=rag 降级、暂停对外 Key、按 6.4 查消耗曲线找异常账号。恢复后必须补上限流（G-03、G-04），否则同样故障会复发。

场景 4：答案出现半截就停了

流式已发出的内容收不回来。此时消息应以 partial 落库，不能标 answered。前端必须给出"待核"标记与重试入口。不要指望它像非流式那样干净——这是上线前必须与业务方确认并接受的取舍。

场景 5：登录后频繁被踢下线

data/.auth_secret 变了（被重建、被覆盖、容器未挂载持久卷）。多实例部署时各实例密钥不一致也会如此，此时必须统一用 AUTH_SECRET 环境变量。

场景 6：制度已上传但问不到

四个可能：effective_from 在未来（待生效不入索引）、重建未完成（看 rebuilding）、doc_id 已有同版本被拒（KB_003，旧版仍在）、切片为空（PDF 无文本层）。

场景 7：Agent 说"已为您建单"，但列表里没有

模型谎报写操作。系统会核对"模型说了什么"与"实际发生了什么"，命中时状态置 inconsistent，答复开头加"本次并没有实际完成建单"。处置：查 agent_traces 确认工具被拒的原因码，不要手工补单——补单会绕过闸门。

场景 8：同一张单出现两条记录

先看是否命中幂等键。create_draft 第一步查 idempotency_key，命中返回上次那张单且 created=false；这是唯一一条"没有凭证也能返回成功"的路径，因为它没有产生新写入。若仍重复，说明调用方每次换了幂等键，属接入方缺陷，须在集成侧修正。

7.4 取证

要回答的问题查哪里
这次请求发生了什么按 trace_id 串日志与 chat_messages
为什么这么判断agent_traces（每次工具调用一条：tool_name、args、ok、错误码）
用的是哪一版提示词chat_messages.prompt_version
引用来自哪条原文citations 到 chunk_id，再到 chunks.jsonl
谁查过、谁确认audit_event、message_audits

取证的纪律：只读、只追加。审计表在数据库层面收回 UPDATE 与 DELETE 权限，任何"修一下日志"的诉求都必须拒绝。

8.2 五类场景预案

预案 A：模型服务不可用

  1. 确认是厂商故障还是本侧配置（LLM_002 与 LLM_003 的区别）；
  2. 厂商故障：切备用 LLM_PROVIDER，或置 AGENT_DEFAULT_MODE=rag 观察；
  3. 仍不可用：置 AGENT_ENABLED=0，页面公告"当前仅提供制度检索，暂不支持建单"；
  4. 全程保持历史会话可查，不要让系统整体变成白屏。

预案 B：疑似数据泄露

  1. 立即停服，断开对外 /api/v1；
  2. 导出 audit_event 中 view 与 export 事件，锁定时间窗与账号；
  3. 核查导出记录（每次导出必须写 export 事件，含行数与用途声明）；
  4. 未查明前不恢复服务，不修日志，不覆盖库。

预案 C：发现越权访问

  1. 保留 deny 事件与请求体，不做脱敏；
  2. 吊销相关账号与 API Key；
  3. 复核该账号近 30 天的 view 记录，评估影响范围；
  4. 按一级事件上报。

预案 D：审计链断裂或记录被改

这是停止条件之一，没有"继续观察"的选项。立即暂停试点，按 S2 处理：保留现场、导出最近一次校验通过的快照、由质量负责人确认处置方案。

预案 E：错误单据已提交

当前没有撤销接口（G-13），只能改 SQL。因此处置必须走双人确认：一人执行、一人复核，执行前 dry-run 打印将受影响的单据，执行后留痕并 30 分钟内通知到员工。模板须经业务方审核，不能临时手写 SQL。

九、安全与合规运行要求

9.1 权限模型

角色可提交可确认可导出可改口径可停试点

三条不可协商的边界：质量负责人不代授审批权；模型与系统无任何可写 confirm 的主体；越权拦截在 API 网关与状态机两处执行，不依赖提示词。

9.2 脱敏与 PII

数据面当前状态要求
员工档案查询输出已具备证件号、银行卡、手机仅保留后 4 位，星号数等于原长度减 4
变更单明细 items缺失（G-02）账号须为掩码或密文；order_hash 仍可用规范化值校验；审计需要时受控解密
Agent 轨迹 args缺失（G-02）同上，建单场景是最需要保护的数据
应用日志部分（G-05）命中 PII 正则即逐条确认；http_post_json 不得记录 payload

每日 PII 扫描命令（命中即逐条确认，测试数据除外）：

扫描命令

grep -rEo '([0-9]{17}[0-9Xx]|1[3-9][0-9]{9}|[0-9]{16,19})' logs/ data/*.log 2>/dev/null | sort -u | head

9.3 密钥管理

密钥位置要求
data/.auth_secret文件必须持久化；丢失等于全员掉线；多实例必须统一用 AUTH_SECRET
LLM_API_KEY.env不得入库、不得进日志、不得写进提示词；.env 已被 .gitignore 排除
gate_secret配置留空则从 auth_secret 派生（HMAC-KDF，不直接复用）
API Key（对外）库中存 sha256明文只打印一次；按季度轮换

轮换纪律：任何密钥变更都要在变更单记录影响面（会不会踢人、会不会使凭证失效），并在低峰执行。GATE_TOKEN_TTL_SECONDS 的调整属安全参数变更，同样走变更评审。

9.4 审计留痕

审计要回答四个问题，缺一不可：

问题记录方式载体
谁查过每次 view 与 export 写事件（含 IP、角色、查询条件）audit_event
用哪个版本version_id 加 version_no 加 received_at 三元组audit_event
提了什么建议系统建议以 propose 事件独立记录，永不覆盖原值audit_event.payload
谁确认confirm 事件与 confirm_by 双写，两处一致才算有效两处

硬约束：审计只追加，无 UPDATE 与 DELETE 权限；每次导出必须写 export 事件；哈希链每日校验一次，断链即触发 S2。

改动层风险附加要求

检索（切片、融合、闸门）高必须重跑评测，clause@3 不得低于阈值

前端与文案低回归主要路径

10.3 变更评审清单

任何进入生产的变更，评审时逐条回答，答不出即不通过：

  1. 这个变更会不会改变已有答案？请举例说明。
  2. 回滚方式是什么？多久能回？
  3. 需要重建索引吗？重建期间服务是否可用？
  4. 涉及数据库迁移吗？备份做了吗？能否退回旧代码？
  5. 影响哪些角色？需要通知谁？
  6. 有没有对应的验证用例？在哪跑？
  7. 变更后哪个指标应该变化？变了没有？
