## 一、文档说明

### 1.1 编制目的

本手册解决一个问题：系统从项目组交到运维和业务运营手里之后，**在没有原开发人员的情况下，如何让它稳定跑起来、坏了怎么修、谁能动它、动完留什么痕**。

手册不重复讲业务价值和技术选型理由——那些在《薪酬服务变更核对系统 项目方案》与《设计说明》里。手册只讲**操作**：命令、路径、阈值、判定条件、处置动作、责任人。

### 1.2 适用范围

适用于单实例部署、单批次试点的当前版本。系统在这套约束下是完整可用的；超出约束的部分（多实例、全量铺开、多客户并行）不在本手册覆盖范围内，需要重新评估——原因见 2.5 节。

### 1.3 读者对象

| 读者 | 主要关注章节 |
|---|---|
| 运维工程师（SRE） | 三、五、六、七、八章 |
| 实施与集成开发 | 三、四、七、九章 |
| SSC 管理员（业务侧） | 四、五、九章 |
| 上线评审与安全 | 二、六、八、九章，附录 D |

### 1.4 术语

| 术语 | 含义 |
|---|---|
| Chunk（切片） | 制度文档按条款切分后的最小检索单元，编号形如 `POL-CMP-2026-001#c003` |
| 拒答（refused） | 检索无有效证据时系统直接返回"制度里没有依据"，不调用模型、不消耗 token |
| partial | 答案已生成但存在告警（未溯源数字、引用异常等），需人工复核 |
| 闸门（gate） | Agent 建单前的四层顺序约束，含一次性 `validation_token` 与人工 `confirm_token` |
| 轨迹（trace） | `agent_traces` 表中记录的工具调用流水，回答"它为什么这么判断"的唯一依据 |
| 制度参数 | `policy_params` 表中的结构化数值，每个参数必须挂 `source_clause` |

## 二、系统交付概述

### 2.1 系统定位

系统的核心风险不是"查不到制度"，而是**答得像制度、其实不在制度里**。因此本期交付的能力围绕三件事构建：答案必须能回到原文、数字不由模型产出、没有依据就闭嘴。

能力边界同样是交付内容的一部分，运维需要清楚哪些事系统**永远不会做**：

| 系统不做 | 表现 |
|---|---|
| 不写回业务系统 | 没有回写接口，建单止于草稿 + 人工确认 |
| 不自动审批、不自动放行 | L3/L4 分级不给凭证，模型拿不到凭证就建不了单 |
| 不编造最新状态 | 读取失败保留快照并标注"停留于某时刻"，不重试业务动作 |
| 不做真实薪资计算与发放 | 无工资表生成、无付款、无报税动作 |
| 不对外发消息 | 无消息推送通道，转人工只记录不触达外部 |

任何要求系统"自动修数据""自动确认""直接对外发结果"的需求，都属于越界需求，运维应按变更管理流程拒绝而非临时变通。

### 2.3 运行架构

系统是四层单向依赖结构，运维排障时可以按层定位问题：

```text
入口层    CLI（main.py）  /  HTTP（FastAPI：/chat SSE、/admin、/api/v1）
              │
编排层    orchestrator：检索 → 组装 prompt → 生成 → 护栏 → 引用
              │
    ┌─────────┼─────────┐
检索层  hybrid（向量 + BM25 + RRF）│ llm 适配层（唯一出网口）│ guard（程序化复核）
              │
持久层    store/db.py → store/chat_repo.py（只有这里写 SQL）
```

排障时这条依赖顺序就是排查顺序：入口层报错先看协议与鉴权，编排层报错看检索与模型，持久层报错看库与锁。**唯一出网口是 `core/llm/http.py`**，所以"是否真的调了模型"只要看这一个地方的日志就能确定。

### 2.4 运行拓扑

| 项 | 取值 | 说明 |
|---|---|---|
| 部署形态 | 内网单机、单实例 | 多实例的两处障碍见 2.5 |
| 服务地址 | `http://127.0.0.1:8000` | 登录页 `/login`，员工页 `/`，后台 `/admin` |
| 数据库 | SQLite 单文件 | `BEGIN IMMEDIATE` 短事务，写并发不高 |
| 索引 | 本地文件 | FAISS + `chunks.jsonl`，重建即全量 |
| 模型 | OpenAI 兼容 HTTP 接口 | `LLM_PROVIDER` 切换厂商，只改三个变量 |
| 反向代理 | 建议 Nginx | 终结 HTTPS，设 `COOKIE_SECURE=1` |
| 时区 | 服务器与业务同区（Asia/Shanghai） | 双时间戳与"过期单"判定依赖时区一致 |

### 2.5 关键约束

以下四条是当前实现的客观限制，不是配置项，**不能靠调参绕过**：

1. **索引重建与提示词缓存是单实例语义**。多实例部署时，重建锁与缓存失效不跨进程，会出现"一台已用新制度、一台还在用旧制度"。要做多实例，必须先把这两件事挪到外部队列或共享存储。
2. **限流是进程内滑动窗口**。对外 `/api/v1` 多实例时实际上限 = 实例数 × 配额。
3. **网页端 JWT 路径当前没有限流**（见 2.6 缺口 G-03）。在补齐之前，不得把员工入口直接暴露到公网。
4. **BM25 是内存倒排**。千条切片内无感，上万条需要换 `tsvector` 或独立检索服务。

### 2.6 交付现状与已知缺口

本节是全手册中最需要被读到的一节。下表如实反映当前代码状态，`已具备` 指有实现且有测试，`部分` 指有实现但缺一环，`缺失` 指尚无实现。

| 编号 | 能力 | 状态 | 上线影响 | 上线前必须动作 |
|---|---|---|---|---|
| G-01 | 员工档案查询出口脱敏 | 已具备 | — | 回归验证星号位数 |
| G-02 | 变更单明细与 Agent 轨迹中的账号明文 | 缺失 | **阻塞**：建单环节恰好是最需要保护的数据 | 落地掩码或加密列，见 9.2 |
| G-03 | 网页端（JWT）提问限流 | 缺失 | **阻塞**：一个循环脚本即可打空当月预算 | 补单账号并发 1、20 次/分钟 |
| G-04 | 全局 LLM 并发与日预算 | 缺失 | **阻塞**：预算耗尽表现为"全站答不出来" | 全局并发 ≤ 8，80% 告警、100% 降级固定 RAG |
| G-05 | 应用日志不含 PII | 部分 | 阻塞项，需实测确认 | 跑 10 次问答 + 1 次建单后 grep 扫描 |
| G-06 | 保留期与到期删除可执行 | 缺失 | 阻塞项，合规要求 | 提供 `data purge` 命令或定时任务，留批次号与条数 |
| G-07 | 供应商 429/5xx 退避 | 部分 | 有重试，缺熔断 | 连续失败 5 次熔断 60 秒 |
| G-08 | LLM 超时与空回复处置 | 部分 | 不得以 `answered` 落库 | 60 秒内返回带 `trace_id` 的错误，可一键重试 |
| G-09 | 降级开关 | 部分 | 30 秒内生效，无需改代码 | 验证 `AGENT_ENABLED=0`、`AGENT_DEFAULT_MODE=rag` |
| G-10 | 代码/镜像回滚 | 部分 | 目标 ≤ 15 分钟 | 预发演练一次并计时 |
| G-11 | 数据库迁移可逆 | 部分 | 迁移前自动备份（表重建为 `DROP`，不可逆） | 备份恢复演练至独立目录 |
| G-12 | 索引蓝绿切换 | 部分 | 索引落盘是原地覆盖 | 改为目录级切换，回滚 ≤ 1 分钟 |
| G-13 | 数据修复与撤销 | 缺失 | 错单目前只能改 SQL | 提供带 dry-run 的双人确认脚本 |

**处置原则**：G-02～G-06 为阻塞项，未通过不得上线；未通过项需技术负责人与业务方共同签字接受，默认不允许。其余为建议项，可带风险上线但须书面记录在附录 D 的签字页上。

## 三、环境与部署

### 3.1 前置条件

| 类别 | 要求 |
|---|---|
| 操作系统 | Windows Server 2019+ 或 Linux（内网单机） |
| Python | 3.12（本项目后端栈：FastAPI + SQLAlchemy 2.0 风格，`core/` 与 `store/` 均在 3.12 验证） |
| 内存 | ≥ 4 GB（索引常驻内存，千条切片量级） |
| 磁盘 | ≥ 20 GB（库、制度原文、索引、日志） |
| 网络 | 出网仅需模型厂商 HTTPS 端点；其余全部内网 |
| 端口 | 8000（应用）；反向代理 443 |
| 浏览器 | Chrome / Edge（语音输入依赖 Web Speech API） |

### 3.2 目录规划

```text
<deploy_root>/
├─ src/my_tool/            # 应用代码
├─ scripts/                # deploy.sh、run_server.bat、eval_agent.py
├─ eval/                   # agent_cases.json
├─ config/default.yaml     # 配置基线
├─ .env                    # 环境变量（已被 .gitignore 排除，禁止提交）
├─ logs/                   # 应用日志（须做 PII 扫描）
└─ data/                   # 唯一需要备份的目录，见 5.7
   ├─ chat.db              # 主库
   ├─ chat.db.bak.*        # 备份
   ├─ policy/              # 制度原文 + uploads/
   ├─ index/               # 派生物，可重建
   └─ .auth_secret         # 认证密钥，必须持久化
```

**目录纪律**：`data/` 是唯一需要备份的目录；`data/index/` 是派生物，可以删、可以重建，不要为它做增量备份——那会在回滚时把新旧切片混在一起。

### 3.3 部署步骤

以下步骤按顺序执行，每步都有可验证的产出，不建议合并执行：

```bash
# 1. 安装依赖（建议虚拟环境）
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e .

# 2. 配置环境变量（复制模板后逐项填写，禁止直接改 default.yaml 承载密钥）
cp .env.example .env

# 3. 初始化库表与演示数据（首次部署）
payroll-check data seed        # 写入 16 个制度参数 + 5 份演示人事档案
payroll-check data params      # 核对 16 个参数与条款出处是否齐全

# 4. 构建索引（首次必须执行）
payroll-check build

# 5. 自检：配置与索引 manifest
payroll-check info

# 6. 启动服务
payroll-check serve            # 或 Windows 双击 scripts\run_server.bat
```

**首次启动必须看一眼控制台**：管理员账号会自动创建，密码取自 `ADMIN_SEED_PASSWORD`；未设置时随机生成并**只在启动日志里打印一次**。错过这一行只能用 `user reset` 重置。

### 3.4 环境变量

| 变量 | 默认 | 说明 | 变更影响 |
|---|---|---|---|
| `LLM_PROVIDER` | `mock` | `mock`/`openai`/`deepseek`/`qwen`/`moonshot`/`zhipu`/`ollama`/`vllm` | 需重启 |
| `LLM_API_KEY` | 空 | 未配置时自动降级为 mock | 需重启；缺失表现为答案质量骤降 |
| `LLM_BASE_URL` / `LLM_MODEL` | 厂商默认 | 换自建网关只改这两项 | 需重启 |
| `EMBEDDING_PROVIDER` | `hash` | **生产必须替换**，hash 无语义能力 | 变更后必须重建索引 |
| `TOP_K` / `RECALL_K` | `3` / `12` | 送入 prompt 条数 / 单路召回数 | 需重启 |
| `MIN_VECTOR_SCORE` / `MIN_BM25_SCORE` | `0.25` / `4.0` | 拒答闸门阈值 | **换向量模型必须重标定**，否则"该答的不答" |
| `INDEX_DIR` | `data/index` | 索引目录 | 改这一项即可完成索引回滚 |
| `AUTH_REQUIRED` | `1` | `0` = 演示模式，所有访问按管理员处理 | **仅演示与回归测试**，生产禁止为 0 |
| `COOKIE_SECURE` | `0` | 走 HTTPS 时设 `1` | 需重启 |
| `AUTH_SECRET` | 空 | 多实例统一密钥；单实例留空则用 `data/.auth_secret` | 变更会使所有 JWT 失效 |
| `ADMIN_SEED_PASSWORD` | 空 | 首次建管理员用 | 仅首次生效 |
| `GATE_TOKEN_TTL_SECONDS` | `600` | 建单校验凭证有效期 | 太短导致长对话反复校验，太长导致旧校验可复用 |
| `PROMPT_CACHE_SECONDS` | 默认 | 多 worker 下提示词生效延迟 | 单 worker 立即生效 |
| `AGENT_ENABLED` | 依配置 | Agent 能力是否可用 | 需重启；降级手段之一 |
| `AGENT_DEFAULT_MODE` | `rag` | `/chat` 默认走 `rag` 还是 `agent` | 需重启 |
| `OFFSCOPE_ANSWER` | 默认 | 越界问题的统一话术 | 需重启 |

关于阈值的硬提醒：`MIN_VECTOR_SCORE` / `MIN_BM25_SCORE` 的当前值是按 hash 占位向量标定的（有效问题 0.27~0.38，越界问题 ≤0.12）。换成 bge-m3 这类真实向量模型后相关分会整体抬高，**不重标定就会出现大范围误拒答**——这类故障的典型表现是"系统突然什么都不知道了"，但日志里没有任何错误。

### 3.5 账号初始化

```bash
payroll-check user list                                  # 查看现有账号
payroll-check user add --username zhangsan --name "张三" --role employee
payroll-check user add --username lisi --name "李四" --role admin --password "Pass1234"
payroll-check user reset --username admin                # 随机生成新密码并打印
```

不传 `--password` 时系统随机生成并打印，这比自己想一个更安全，也能避免全公司共用一个密码。本期没有用户管理页面（两个角色撑不起一套 CRUD 界面），账号维护走命令行。

### 3.6 上线门禁

上线评审按下列四条执行，三条以上任一不满足则不上线：

1. 25 项检查中所有【阻塞】项通过；未通过项须技术负责人 + 业务方共同签字接受。
2. 上线前 24 小时冻结代码与提示词，只接受修复阻塞项的热修。
3. 上线后 2 小时双人值守，盯四个指标：错误率、首字延迟 P95、LLM 429 比例、注入拦截次数。
4. 首日抽样 20 条真实问答 + 5 张真实单据人工复核，准确率低于 95% 即启动回滚评估。

## 四、系统初始化配置

### 4.1 制度入库

两条路径：命令行 `build`（首次全量）与后台「知识库」页上传（日常增量）。

后台路径：知识库页 → 选文件 → 填标题/版本/生效期 → 上传。约束如下：

- 支持 `.md` / `.txt` / `.pdf`，单文件 ≤ 10 MB；
- 上传后**不会立刻生效**，触发后台重建，页面顶部显示"重建中"；
- 重建期间员工照常提问，用的是上一版索引；完成后原子热切换；
- 同一 `doc_id` 已存在时被拒绝（`KB_003`），制度不能静默覆盖。

**PDF 的边界必须说清**：只支持有文本层的 PDF。扫描件直接报错并提示需要 OCR。这是刻意设计——静默产出一份空文档比报错糟糕得多：上传成功、问答永远答不出，还找不到原因。表格多的制度建议用 Markdown，pypdf 只给文本流，行列关系会丢。

### 4.2 制度参数与员工档案

```bash
payroll-check data seed      # 16 个参数 + 5 份档案（含一个缺法人归属的样本，用于验证阻断）
payroll-check data params    # 核对参数与条款出处
```

**数值只从 `policy_params` 来，每一行都必须有 `source_clause`**。参数缺失时系统返回 `missing`，这是给 Agent 的行动信号：必须转人工，不许猜。地区优先级为"本地区 → 全国默认（`region_code=''`）→ `missing`"。

当前只有 310000 一套参数，其他地区会全部 `missing`，这是刻意行为，不是缺陷。

### 4.3 部门与组织归属

```bash
payroll-check dept add --name 华东区域 --code EC
payroll-check dept add --name SSC上海 --parent 华东区域
payroll-check dept assign --username zhangsan --dept SSC上海 --title 高级薪酬专员
payroll-check dept list
```

只做两级是有意的：SSC 要回答的是"华东区这个月多少人在问冻结期、拒答率多少"，两级够用；更深的组织树属 HR 主数据，应对接而非自建。

统计口径必须看清，否则数字会被误读：

| 项 | 口径 |
|---|---|
| 提问数 | **次数**，一人问 10 次算 10 次 |
| 参与人数 | 该组有提问的不同账号数 |
| 拒答率 | `refused / (answered + partial + refused)`，排除流式占位行 |
| 时间窗 | 固定近 30 天 |
| 未归属 | 未挂部门或部门已删的问答合成一组 |

### 4.4 对外 API Key

```bash
payroll-check apikey add --name hr-portal --owner 张工 --rate-limit 60
payroll-check apikey list
payroll-check apikey revoke --id 3f2a1b0c      # 支持短 id
```

明文**只打印一次**，库里只存 sha256。丢了就吊销重发，不要试图找回。Key 无过期时间，只有"吊销"，定期轮换要靠人——建议写进运维日历，按季度轮换一次。

### 4.5 Agent 开关

| 变量 | 作用 |
|---|---|
| `AGENT_ENABLED` | 能力是否可用（关掉后 Agent 模式不可选） |
| `AGENT_DEFAULT_MODE` | `/chat` 默认走 `rag`（固定检索）还是 `agent`（工具链） |

上线初期建议 `AGENT_DEFAULT_MODE=rag`，观察两周后再切换默认值。Agent 模式的最终答案不是真流式（工具循环跑完后一次性发 `delta`，前端用打字机弥补观感），对超长对话的首字延迟影响明显。

## 五、日常运行

### 5.1 启停

| 动作 | 命令 | 说明 |
|---|---|---|
| 启动 | `payroll-check serve` | 前台运行；生产建议由 systemd / NSSM 托管 |
| 启动（Windows） | `scripts\run_server.bat` | 起服务并自动打开登录页 |
| 停止 | Ctrl+C 或服务管理器 | 无优雅停机队列，SSE 连接会中断，客户端会收到 `CLI_001`（仅日志） |
| 重启 | 见上 | 密钥取自 `data/.auth_secret`，重启不踢人；除非该文件变了 |

**重启会导致的可见影响**：进行中的流式回答中断；索引重建任务丢失，需重新触发。因此重启窗口应避开业务高峰（建议 20:00 之后）。

### 5.2 每日巡检（10 分钟）

按顺序走一遍，全部通过即结束：

| # | 检查 | 方法 | 异常判据 |
|---|---|---|---|
| 1 | 服务存活 | `curl http://127.0.0.1:8000/healthz` | 无响应 / `ready=false` |
| 2 | 索引状态 | 同上，看 `chunk_count`、`built_at`、`rebuilding` | `chunk_count` 与昨日差异无解释；`rebuilding` 长期为 true |
| 3 | 概览页 | `/admin` | 黄条提示（演示模式）、待处理违规堆积 |
| 4 | 当日问答量 | `/admin` 概览 | 与近 7 日均值偏离 ±50% 需问一句为什么 |
| 5 | 拒答率 | `/admin` 概览 | 单日 > 30% 视为异常（可能索引坏了或阈值漂移） |
| 6 | 错误日志 | `grep -E 'ERROR|Traceback' logs/*.log` | 出现未捕获异常、上游 5xx |
| 7 | 流式中断 | 日志中 `CLI_001` 频次 | 突增说明前端或网络有问题 |

| 成本核对 | token 日消耗对照供应商账单，偏差 < 15% | 财务 BP + 运维 |

### 5.4 制度换版与回滚

这是本期最重要的运行变化。旧做法是"先删旧版再传新版"，两步之间索引里没有这份制度，员工提问会直接拒答；真实制度每年都改，这个窗口期就是事故窗口。

**正确做法**：知识库页 → 上传 → **保持 `doc_id` 不变，版本号 +1** → 上传。系统在同一事务内完成：新版入库（`active`）、旧版置 `superseded`、触发重建，全程没有"制度不见了"的时刻。

| 状态 | 含义 | 问答是否使用 |
|---|---|---|
| `active` | 现行版本 | 是（且生效日已到） |
| `superseded` | 被新版替代，留档 | 否 |
| `deleted` | 软删，文件保留 | 否 |

三条硬规矩：

1. **同 `doc_id` + 同版本重复上传会被拒绝**（`KB_003`）。要改内容就提升版本号，否则"当时生效的是哪一版"说不清。
2. **版本号是数字，不做大小比较**。系统只用它判"是不是同一版"。展示用版本串（`v1.0`、`2026-A`）填在「版本标识」里，与纸质文件对照。
3. **待生效版本不进索引**。`effective_from` 填未来日期时，这一版入库但不进索引，列表页显示「待生效」徽标。

**回滚**：文档详情 → 版本历史 → 「回滚到本版」。回滚不是删除：把旧版重新置 `active`，当前版变 `superseded`，再重建索引。新版写错了用回滚，**不要用删除**——删掉会让制度整体消失，回滚则全程有依据。

### 5.5 索引重建

全量重建是唯一方式（FAISS 索引无法局部摘除向量），但只有内容变化的切片才重新向量化，向量缓存在 `data/index/vec_cache_*`。

| 场景 | 动作 | 预计影响 |
|---|---|---|
| 制度上传/换版/回滚 | 后台自动触发 | 重建期间用旧索引，无服务中断 |
| 换向量模型 | 必须手动重建（`payroll-check build`） | 重建期间不可检索旧索引，需安排窗口 |
| 索引损坏 | 删除 `data/index/` 后 `build` | 全量重建，耗时与切片数成正比 |

重建失败不影响线上检索——重建失败时旧索引仍在使用，但必须当天处理，否则下一次换版就没有退路。

### 5.6 提示词变更

提示词页 → 编辑 → 「用草稿预览」→ 保存。三条约束：

1. **保存 = 新建版本**，历史永远在，可回滚到任意版本；
2. `{context}` 与 `{question}` 两个占位符必须保留，否则拒绝保存——少了 `{context}` 模型只拿到问题、没有资料，它会直接开始编，而事故发生在员工页；
3. 页面上的「系统强制追加」改不了：角标格式是系统契约不是话术，护栏按 `[1] [2]` 核对引用，模型不标角标答案就会被判"引用缺失"。

生效时机：保存后下一个问题就用新版（单 worker 立即生效；多 worker 最长等 `PROMPT_CACHE_SECONDS`）。每条回答都记下当时用的 `prompt_version`，审计页可查。

**流程要求**：提示词改动属高风险变更，须走 10.3 的评审清单，且改动后必须重跑注入红队用例——提示词调优会悄悄削弱拒绝倾向，这是最容易回归的地方。

### 5.7 备份与恢复

需要备份的只有三样：

| 对象 | 路径 | 频率 | 保留 |
|---|---|---|---|
| 主库 | `data/chat.db` | 每日 + 每次变更前 | 30 天 |
| 制度原文 | `data/policy/`（含 `uploads/`） | 每周 + 每次上传后 | 全程 |
| 认证密钥 | `data/.auth_secret` | 一次性归档到密钥管理 | 长期 |

`data/index/` 是派生物，不在备份范围，重建即可。

```bash
# 备份
cp data/chat.db "data/chat.db.bak.$(date +%Y%m%d%H%M)"
cp -r data/index "data/index.bak.$(date +%Y%m%d%H%M)"

# 恢复（先停服务）
# 1) 丢弃当前库，换回备份
# 2) 若备份与当前索引不匹配，删除 data/index/ 后 payroll-check build
# 3) 启动并跑 5.2 的巡检 1~3 项
```

**恢复演练要求**：上线前必须完成一次"备份 → 恢复至独立目录 → 校验行数"的完整演练并记录耗时。备份没被恢复验证过，等于没有备份。

### 5.8 日志与审计数据

| 数据 | 载体 | 留存要求 | 处置 |
|---|---|---|---|
| 应用日志 | `logs/` | 30 天 | 每日轮转，含 PII 即整改 |
| 问答记录 | `chat_messages` | 试点全程 | 到期按 G-06 的清理任务删除 |
| Agent 轨迹 | `agent_traces` | 试点全程 | 每次工具调用一条，不可删改 |

| 制度原文 | `data/policy/` | 按档案要求 | 不随问答记录清理 |

保留期与到期删除当前尚未实现（G-06），上线前必须补齐，否则"承诺删除但删不掉"是合规瑕疵而非技术债。

## 六、监控与告警

### 6.1 健康检查

| 接口 | 用途 | 返回 |
|---|---|---|
| `GET /healthz` | 内部探活 | 索引 / 模型 / 数据库状态；索引坏也返回 200，需看字段 |
| `GET /api/v1/healthz` | 对外探活（需 Bearer） | `{"ready","chunk_count","doc_count","built_at","rebuilding"}` |

内部 `/healthz` 刻意在索引损坏时仍返回 200，是为了让探针区分"进程死了"与"能力降级"。**告警规则必须读字段，不能只看状态码。**

### 6.2 技术指标

| 指标 | 采集方式 | 阈值 | 处置 |
|---|---|---|---|
| 错误率（5xx + `SRV_001`） | 日志/网关 | > 2% 持续 5 分钟 | 七章排障 |
| 首字延迟 P95 | SSH 帧时间戳 | > 8 秒 | 查模型上游与检索耗时 |
| LLM 429 比例 | `llm/http.py` 日志 | > 5% | 降并发 / 换配额 |
| 注入拦截次数 | 红队用例 + `deny` 记录 | 单日异常升高 | 安全事件，按 8.2 处置 |
| 上游超时率（`LLM_001`） | 日志 | > 3% | 检查厂商状态页 |
| 索引重建时长 | 后台任务日志 | > 10 分钟 | 排查切片数与缓存命中 |

### 6.3 业务质量指标

质量指标比技术指标更早暴露问题，建议每日看一次：

| 指标 | 计算口径 | 健康区间 | 异常含义 |
|---|---|---|---|
| 拒答率 | `refused / (answered + partial + refused)` | 10%~25% | 骤升 = 索引坏或阈值漂移；长期 0 = 闸门失效 |
| partial 率 | `partial / 总回答` | < 10% | 升高 = 未溯源数字增多，模型在编 |
| 零引用答案 | `answered` 且 `citations` 为空 | 0 | 护栏失效，属阻塞级 |
| 未溯源数字 | `guard.unverified_numbers` 非空条数 | 趋势下降 | 提示词或资料质量问题 |
| 反馈负向率 | `feedback` 统计 | < 15% | 结合样本看是知识缺口还是表达问题 |

系统预筛的四条规则（R1 未溯源数字、R2 拒答却出现金额、R3 推测语气、R4 正常作答无引用）是**提示不是结论**，且实时计算不落库。只有人工标记才进 `message_audits`——这样"确认违规 3 条"这个数字才永远可信。

### 6.4 成本监控

```sql
-- 当日 token 消耗
SELECT sum(token_in + token_out) FROM chat_messages WHERE date(created_at) = date('now');
```

预算控制要求：80% 告警、100% 自动降级固定 RAG 并在页面公告。当前该能力尚未实现（G-04），上线前必须以外部手段兜底（如厂商侧配额上限 + 人工每日看数），不能留空。

### 6.5 告警分级

| 级别 | 定义 | 响应时限 | 通知 |
|---|---|---|---|
| P1 | 全站不可用、数据泄露、越权访问成功 | 15 分钟 | 值班电话 + 技术负责人 + 业务负责人 |
| P2 | 部分功能不可用、错误率 > 5%、预算耗尽 | 1 小时 | 值班群 + 技术负责人 |
| P3 | 单点异常、质量指标劣化 | 4 小时 | 值班群 |
| P4 | 体验问题、文档不一致 | 次工作日 | 工单 |

## 七、故障处理

### 7.1 排障总流程

按分层顺序定位，不要跳步：

```text
1. 现象分类：全站 / 单功能 / 单用户 / 数据不准
2. 看 healthz：ready、chunk_count、rebuilding、doc_count
3. 看错误码：有码走 7.2 表；无码看 7.3 场景
4. 看 trace_id：从用户界面或日志拿到，串起一次完整请求
5. 看轨迹：涉及建单/判定的，查 agent_traces 的 tool_name 与 args
6. 处置：先恢复（降级/回滚），再定位根因
```

**处置优先级原则**：能通过降级开关恢复的，先降级；不能的，回滚代码或索引；以上都不行的，切只读公告并转人工。不要在故障现场改代码。

### 7.2 错误码速查

| 码 | HTTP | 含义 | 处置 |
|---|---|---|---|
| `REQ_001` | 400 | 请求非合法 JSON | 调用方问题，看接入方日志 |
| `REQ_002` | 400 | 缺少必填参数 | 同上 |
| `REQ_003` | 400 | 问题为空 | 前端校验缺失 |
| `REQ_004` | 400 | 问题过长（上限 500 字） | 提示用户拆分 |
| `REQ_005` | 400 | 会话标识格式不正确 | 清本地会话 |
| `SES_001` | 404 | 会话不存在或被清理 | 自动新建重发 |
| `SES_002` | 410 | 会话已删除 | 自动新建 |
| `SES_004` | 409 | 该会话正在生成回答 | 前端应禁用发送；频繁出现说明流未正常收尾 |
| `IDX_001` | 503 | 索引未就绪 | `payroll-check build`；查 `data/index/` 是否完整 |
| `IDX_002` | 503 | 索引与当前向量模型不一致 | **必须重建索引**，不要改配置迁就旧索引 |
| `LLM_001` | 504 | 生成超时 | 查厂商状态；连续出现按 6.2 告警 |
| `LLM_002` | 502 | 模型配置/鉴权错误 | 检查 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` |
| `LLM_003` | 502 | 模型服务不可用 | 厂商 5xx，重试 + 降级 |
| `SRV_001` | 500 | 未捕获异常 | 带 `trace_id` 查堆栈 |
| `SRV_002` | 429 | 并发超限 | 看 `detail.retry_after`；调并发或配额 |
| `AUTH_001` | 401 | Key 缺失/错误/已吊销（不区分） | 重新签发；不区分是为了避免成为枚举接口 |
| `KB_003` | — | 同 `doc_id` 同版本重复 | 提升版本号，或先删除该版再传 |
| `AGT_001` | — | 校验凭证签名无效 | 伪造或篡改，安全事件 |
| `AGT_002` | — | 凭证过期 | 默认 600 秒；长对话需重新校验 |
| `AGT_003` | — | 凭证内容与提交不一致 | **校验 A 建 B**，属越权尝试，需审计 |
| `AGT_004` | — | 凭证已使用 | 一次性凭证的正常代价；重试应命中幂等键 |
| `AGT_005` | — | 用需复核的凭证硬建 | `verdict != pass`，应转人工 |
| `AGT_007` | — | 越权查询他人档案 | 权限在工具/SQL 层强制，非提示词 |
| `CLI_001` | — | 客户端已断开 | 仅日志与落库，不告警 |

### 7.3 常见故障场景

**场景 1：服务起不来**

先看启动日志首屏。三类原因：端口占用（8000）、`data/.auth_secret` 不可写、迁移失败。迁移在一个事务内，失败会整体回滚，不会留半张表——回滚后可安全重试，但重试前必须先备份。

**场景 2：全部问题都拒答，且无报错**

这是最容易被误判为"模型坏了"的故障。实际最常见原因是闸门阈值与向量模型不匹配（3.4 节）。排查顺序：

1. `payroll-check info` 看 manifest 的 `backend` / `dim` 是否与当前配置一致；
2. 若不一致，重建索引；
3. 若一致，用 `--debug` 跑一个已知有效问题，看两路 `best_vector_score` / `best_bm25_score` 与阈值的关系；
4. 分数整体低于阈值 → 换模型后未重标定，需重新标定而非下调阈值凑数。

**场景 3：全站答不出来，日志里有大量 429**

预算或并发配额耗尽。这是"预算烧完"的典型表现。立即：`AGENT_DEFAULT_MODE=rag` 降级、暂停对外 Key、按 6.4 查消耗曲线找异常账号。恢复后必须补上限流（G-03/G-04），否则同样故障会复发。

**场景 4：答案出现半截就停了**

流式已发出的内容收不回来。此时消息应以 `partial` 落库，不能标 `answered`。前端必须给出"待核"标记与重试入口。**不要指望它像非流式那样干净**——这是上线前必须与业务方确认并接受的取舍。

**场景 5：登录后频繁被踢下线**

`data/.auth_secret` 变了（被重建、被覆盖、容器未挂载持久卷）。多实例部署时各实例密钥不一致也会如此，此时必须统一用 `AUTH_SECRET` 环境变量。

**场景 6：制度已上传但问不到**

四个可能：`effective_from` 在未来（待生效不入索引）、重建未完成（看 `rebuilding`）、`doc_id` 已有同名版本被拒（`KB_003`，旧版仍在）、切片为空（PDF 无文本层）。

**场景 7：Agent 说"已为您建单"，但列表里没有**

模型谎报写操作。系统会核对"模型说了什么"与"实际发生了什么"，命中时状态置 `inconsistent`，答复开头加"本次并没有实际完成建单"。处置：查 `agent_traces` 确认工具被拒的原因码，不要手工补单——补单会绕过闸门。

**场景 8：同一张单出现两条记录**

先看是否命中幂等键。`create_draft` 第一步查 `idempotency_key`，命中返回上次那张单且 `created=false`；这是唯一一条"没有凭证也能返回成功"的路径，因为它没有产生新写入。若仍重复，说明调用方每次换了幂等键——属接入方缺陷，须在集成侧修正。

### 7.4 取证

| 要回答的问题 | 查哪里 |
|---|---|
| 这次请求发生了什么 | 按 `trace_id` 串日志与 `chat_messages` |
| 为什么这么判断 | `agent_traces`（每次工具调用一条：`tool_name`、`args`、`ok`、错误码） |
| 用的是哪一版提示词 | `chat_messages.prompt_version` |
| 引用来自哪条原文 | `citations` → `chunk_id` → `chunks.jsonl` |
| 谁查过、谁确认 | `audit_event` / `message_audits` |
| 数据是否被改过 | 哈希链校验（每日一次） |

取证的纪律：只读、只追加。审计表在数据库层面收回 UPDATE / DELETE 权限，任何"修一下日志"的诉求都必须拒绝。

### 7.5 升级与回滚

**升级顺序**（每次升级都按此执行，不得跳步）：

```bash
# 1. 备份（迁移不可逆，这一步省不得）
cp data/chat.db "data/chat.db.bak.$(date +%Y%m%d%H%M)" && cp -r data/index "data/index.bak.$(date +%Y%m%d%H%M)"

# 2. 停服务

# 3. 更新代码，启动（数据库自动迁移，日志会打印迁移行数）

# 4. 自检三条：login → /chat → agent run
payroll-check ask "冻结期内可以改银行账户吗？"
payroll-check agent run --script happy

# 5. 回归
PYTHONPATH=src python -m pytest -q
```

**回滚三条路径**：

| 对象 | 做法 | 目标耗时 | 前提 |
|---|---|---|---|
| 代码/镜像 | 回退到上一 tag | ≤ 15 分钟 | 不需要改库（迁移遵循"只加不删"） |
| 索引 | 改 `INDEX_DIR` 指向旧目录 | ≤ 1 分钟 | 旧索引产物仍在 |
| 提示词/配置 | 后台「恢复默认」或回滚版本 | ≤ 1 分钟 | 版本表保留最近 N 版 |

索引回滚有一个必须提前做的前提：**落盘是原地覆盖**（`VectorStore.save` 直接写 `chunks.jsonl`），进程内切换是原子的、磁盘不是。因此首次上线前必须补上"备份 + 目录级切换"（G-12），否则"回滚索引"只是一句口号。

## 八、应急响应

### 8.1 应急分级

| 级别 | 判定 | 首要动作 | 决策人 |
|---|---|---|---|
| 一级 | 数据泄露、越权访问成功、审计记录被改 | 立即停服，保留现场 | 安全负责人 |
| 二级 | 全站不可用超过 30 分钟 | 降级或回滚 | 技术负责人 |
| 三级 | 单功能不可用、质量指标严重劣化 | 切只读 + 公告 | 值班负责人 |
| 四级 | 影响面小、有替代路径 | 记录 + 排期修 | 运维 |

### 8.2 五类场景预案

**预案 A：模型服务不可用**

1. 确认是厂商故障还是本侧配置（`LLM_002` vs `LLM_003`）；
2. 厂商故障：切备用 `LLM_PROVIDER`，或 `AGENT_DEFAULT_MODE=rag` + 观察；
3. 仍不可用：置 `AGENT_ENABLED=0`，页面公告"当前仅提供制度检索，暂不支持建单"；
4. 全程保持历史会话可查，不要让系统整体变成白屏。

**预案 B：疑似数据泄露**

1. 立即停服，断开对外 `/api/v1`；
2. 导出 `audit_event` 中 `view` / `export` 事件，锁定时间窗与账号；
3. 核查导出记录（每次导出必须写 `export` 事件，含行数与用途声明）；
4. 未查明前不恢复服务，不修日志，不覆盖库。

**预案 C：发现越权访问**

1. 保留 `deny` 事件与请求体，不做脱敏；
2. 吊销相关账号与 API Key；
3. 复核该账号近 30 天的 `view` 记录，评估影响范围；
4. 按一级事件上报。

**预案 D：审计链断裂或记录被改**

这是停止条件之一，没有"继续观察"的选项。立即暂停试点，按 S2 处理：保留现场、导出最近一次校验通过的快照、由质量负责人确认处置方案。

**预案 E：错误单据已提交**

当前没有撤销接口（G-13），只能改 SQL。因此处置必须走双人确认：一人执行、一人复核，执行前 dry-run 打印将受影响的单据，执行后留痕并 30 分钟内通知到员工。模板须经业务方审核——不能临时手写 SQL。

### 8.3 降级开关

| 开关 | 效果 | 生效时间 | 副作用 |
|---|---|---|---|
| `AGENT_ENABLED=0` | 关闭 Agent 能力 | 重启（目标 30 秒内） | 建单不可用，问答仍可用 |
| `AGENT_DEFAULT_MODE=rag` | 默认走固定检索 | 重启 | 无建单，引用更稳定 |
| `AUTH_REQUIRED=0` | 免登录 | 重启 | **仅演示**，生产禁用 |

| 摘除制度（软删） | 该制度不再被引用 | 重建后 | 相关问题转为拒答 |

## 九、安全与合规运行要求

### 9.1 权限模型

| 角色 | 可提交 | 可确认 | 可导出 | 可改口径 | 可停试点 |
|---|---|---|---|---|---|
| 一线服务专员 | 是 | 否 | 受限（脱敏） | 否 | 否 |
| 流程协调员 | 是 | 否 | 受限 | 否 | 否 |
| 数字化工程师 | 否 | 否 | 受限 | 提议 | 否 |
| 审核与质量负责人 | 否 | 否（不代授审批权） | 是 | 质量口径 | 是 |
| 业务负责人 | 是 | 是 | 是 | 业务口径 | 是 |
| 客户协同代表 | 否 | 否 | 受限 | 用途确认 | 否 |

三条不可协商的边界：质量负责人不代授审批权；模型与系统无任何可写 `confirm` 的主体；越权拦截在 API 网关与状态机两处执行，不依赖提示词。

### 9.2 脱敏与 PII

| 数据面 | 当前状态 | 要求 |
|---|---|---|
| 员工档案查询输出 | 已具备 | 证件号/银行卡/手机仅保留后 4 位，星号数 = 原长度 − 4 |
| 变更单明细 `items` | **缺失（G-02）** | 账号须为掩码或密文；`order_hash` 仍可用规范化值校验；审计需要时受控解密 |
| Agent 轨迹 `args` | **缺失（G-02）** | 同上，建单场景是最需要保护的数据 |
| 应用日志 | 部分（G-05） | 命中 PII 正则即逐条确认；`http_post_json` 不得记录 payload |

每日 PII 扫描命令（命中即逐条确认，测试数据除外）：

```bash
grep -rEo '([0-9]{17}[0-9Xx]|1[3-9][0-9]{9}|[0-9]{16,19})' logs/ data/*.log 2>/dev/null | sort -u | head
```

### 9.3 密钥管理

| 密钥 | 位置 | 要求 |
|---|---|---|
| `data/.auth_secret` | 文件 | 必须持久化；丢失 = 全员掉线；多实例必须统一用 `AUTH_SECRET` |
| `LLM_API_KEY` | `.env` | 不得入库、不得进日志、不得写进提示词；`.env` 已被 `.gitignore` 排除 |
| `gate_secret` | 配置 | 留空则从 `auth_secret` 派生（HMAC-KDF，不直接复用） |
| API Key（对外） | 库中存 sha256 | 明文只打印一次；按季度轮换 |

轮换纪律：任何密钥变更都要在变更单记录影响面（会不会踢人、会不会使凭证失效），并在低峰执行。`GATE_TOKEN_TTL_SECONDS` 的调整属"安全参数变更"，同样走变更评审。

### 9.4 审计留痕

审计要回答四个问题，缺一不可：

| 问题 | 记录方式 | 载体 |
|---|---|---|
| 谁查过 | 每次 `view` / `export` 写事件（含 IP、角色、查询条件） | `audit_event` |
| 用哪个版本 | `version_id` + `version_no` + `received_at` 三元组 | `audit_event` |
| 提了什么建议 | 系统建议以 `propose` 事件独立记录，**永不覆盖原值** | `audit_event.payload` |
| 谁确认 | `confirm` 事件 + `confirm_by` 双写，两处一致才算有效 | 两处 |

硬约束：审计只追加，无 UPDATE / DELETE 权限；每次导出必须写 `export` 事件；哈希链每日校验一次，断链即触发 S2。

### 9.5 数据留存

| 数据 | 留存 | 说明 |
|---|---|---|
| 原始版本 / 修订原因 / 确认人 | 试点期全程 + 约定周期 | 不可覆盖 |
| 审计事件 | 同左，不可删改 | 哈希链保证完整性 |
| 虚构个人字段 | 练习结束按约定删除 | 需可执行 |
| 脱敏样本原文件 | 试点结束后 30 天内清除 | 期限待业务确认 |

| 改动层 | 风险 | 附加要求 |
|---|---|---|
| 入口/协议 | 中 | 契约只增不改，错误码语义不得变 |

| 持久层/迁移 | **高** | 必须备份 + 可逆验证 |
| 前端/文案 | 低 | 回归主要路径 |

### 10.3 变更评审清单

任何进入生产的变更，评审时逐条回答，答不出即不通过：

1. 这个变更会不会改变已有答案？（举例说明）
2. 回滚方式是什么？多久能回？
3. 需要重建索引吗？重建期间服务是否可用？
4. 涉及数据库迁移吗？备份做了吗？能否退回旧代码？
5. 影响哪些角色？需要通知谁？
6. 有没有对应的验证用例？在哪跑？
7. 变更后哪个指标应该变化？变了没有？
