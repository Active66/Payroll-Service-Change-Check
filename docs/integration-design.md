## 0. 现状盘点：0.3 之后还缺什么

0.3 结束时系统"能用"，但离"能交给别家上线"还差四件事。逐条说明，因为它们决定了这一期的边界：

| 缺口 | 具体表现 | 不做的后果 |
|---|---|---|
| **制度版本台账** | 同一 `doc_id` 换版本必须"先删旧版再传新版"，中间窗口期该制度不在索引里 | 换版那一刻员工问"我们制度怎么规定的"会拒答。真实制度每年都改，这个窗口期就是事故窗口 |
| **组织架构位置** | `users` 只有姓名/工号，`chat_sessions` 只有 `user_id` | 后台只能"某个人问了什么"，不能回答"华东区多少人在问工资冻结期"——而这恰恰是 SSC 最想看的 |
| **语音输入** | 电话工单、移动场景下打字成本高 | 只影响体验，不影响正确性，属于"加分项" |
| **集成契约** | 只有内部用的 `/chat`，外部 HR 系统接不进来 | 系统只能当"一个网页"用，不能嵌进 `PayrollServiceChangeCheck` 主流程 |

## 1. 制度版本台账（本期主线）

### 1.1 问题

现有唯一键是 `doc_id`，且 `create_document` 在冲突时直接拒绝（`KB_003`）。所以换版只能是
"删旧 → 传新"，两步之间索引里没有这份制度。而重建要几十秒到几分钟，这段时间的问答是不完整的。

### 1.2 方案：`doc_id + version` 台账 + `effective_from` 生效

数据库层只加两个东西，不动现有语义：

- `policy_documents` 的唯一键从 `(doc_id)` 改为 `(doc_id, version)`；
- 同 `doc_id` 上传新版本时**自动把旧版置为 `superseded`**（不删文件、不删切片），
  索引重建时只取 `active` 且 `effective_from <= 今天` 的版本。

这样"换版"变成一次原子操作：新版本入库 → 旧版下线 → 重建 → 热切换。中间不存在"没有制度"的状态，
因为重建期间用的仍是旧索引；重建完成时新版本已经在里面了。

**版本号比较不做自然排序**，只做"是否相同"。制度版本是 `1.0 / 1.1 / 2.0` 这种人工编号，
试图解析成数字只会踩 `1.10 < 1.9` 这种坑，而系统并不需要判断"谁更新"——传上来的就是新版。

### 1.3 增量新字段

`policy_documents` 加三列（`migrate()` 幂等补列，老库不动）：

| 列 | 用途 |
|---|---|
| `version_label` | 原始版本串（`v1.0` / `2026-A`），展示用；`version` 仍存规范化后的序 |
| `superseded_at` | 被新版替代的时间，`NULL` 表示未被替代 |
| `published_by` | 这次上传是谁做的（审计要求，SSC 要知道谁把制度换掉了） |

**`status` 枚举扩展**：`active / superseded / deleted`。`superseded` 与 `deleted` 的区别是语义：
前者是"被新版替代，历史仍在"，后者是"这份不要了"。列表页默认只显示 `active`，可切换看历史。

### 1.4 生效期前置

`effective_from` 未来日期的新版本允许上传，但重建时**不进入索引**（检索侧本来就有生效期过滤，
但把它挡在建索引阶段更省事，也让"待生效"在后台可见）。后台文档列表增加"待生效"徽标。

## 2. 组织架构（部门 / 岗位）

只做**两级**：`departments(id, name, parent_id)` + `users.department_id / job_title`。

不做完整组织树（多层级、历史沿革、编制管理）：SSC 的审计诉求是"按区域/部门看问答分布"，
两级足够；再深就是 HR 主数据系统的事，应该对接而不是自己造。

新增两条只读接口：`GET /admin/org/departments`（树形）、`GET /admin/org/stats`（按部门聚合问答量、拒答率）。
页面并入概览，不单独开一级菜单——它是个"分析视角"，不是"管理对象"。

## 3. 语音输入（可选能力，开关控制）

**浏览器侧能力，不上传音频。** 用 Web Speech API（Chrome/Edge 内置），识别结果直接填进输入框，
用户可编辑后再发送。理由：

- 零依赖、零成本、零隐私风险（音频不出本机、不进服务端）；
- 若改用服务端 ASR（Whisper 等），要新增 `POST /asr`、音频存储、清理策略、模型部署——这是另一个工期，
  而且**识别错一个字，检索就可能错一条条款**，必须给用户"改完再发"的机会。

不支持语音的浏览器（Firefox/Safari）隐藏麦克风按钮，不报错。

## 4. 集成契约（对外）

给外部系统一个**稳定、窄**的入口，而不是暴露内部全部接口：

| 接口 | 用途 |
|---|---|
| `POST /api/v1/ask` | 一次性问答（非流式），返回答案 + 引用 + 状态。给 HR 系统、工单系统调用 |
| `GET /api/v1/healthz` | 对方做健康检查用，字段与内部 `/healthz` 子集一致 |

`/api/v1/ask` 的鉴权走 `Authorization: Bearer <API_KEY>`（服务端出网调用没有 cookie），
与 JWT 分开：**JWT 是"人"的凭证，API Key 是"系统"的凭证**，混用会导致"员工能拿自己的 token 调外部接口"。

限流：按 Key 每分钟 N 次（默认 60），超限 `SRV_002`。`/chat` 那套 SSE 时序不对外——
外部系统只想要"一问一答 + 引用"，流式对它们没价值，反而把 `no-transform` / 心跳这些细节变成契约负担。

## 5. 失败态（§6.2 的落地检查表）

| 场景 | 现状 | 本期补什么 |
|---|---|---|
| LLM 超时 / 5xx | 已翻译为 `LLM_001/003` | 前端补"重试"按钮（同一 session 续问） |
| 索引重建失败 | `KB_006`，保留旧索引 | 概览页展示上次失败原因（已具备），补"重试重建" |
| 数据库被锁 | `busy_timeout` 5s | 超时翻译为 `SRV_003`，明确"请稍后重试"而不是 500 |
| 上传文件超大 | `KB_002` | 页面提前拦（前端读 `size`），不发到服务端 |

## 7. 明确不做

1. **不做多租户**：`legal_entity_id` 已在表里，但租户隔离涉及数据分区、索引分区、密钥分区，不是加一列能解决的。
2. **不做服务端 ASR**：理由见第 3 节。
3. **不做流式外部接口**：理由见第 4 节。
4. **不做制度富文本编辑器**：制度是 Markdown 文件，编在 Git 里比编在后台好——后台只管"发布哪一版"。

## 8. 验收

| 项 | 判据 |
|---|---|
| 版本切换 | 上传 `doc_id` 相同的新版本，旧版变 `superseded`，问答命中新版内容，全程无拒答 |
| 待生效版本 | `effective_from` 为未来的版本不在索引里，列表页有徽标 |
| 组织 | 按部门聚合的问答量与拒答率与手工核对一致 |
| 语音 | Chrome 下点麦克风能出字，Firefox 下按钮不出现 |
| 外部接口 | 无 Key → 401；Key 错 → 401；超限 → 429；正常 → 答案带引用 |
| 回归 | pytest 全绿（162 → 180+）、pyflakes 无输出、eval 8/8 不退 |
