# 阶段 4 · 集成与上线前加固 使用说明

面向：SSC 管理员、集成开发、运维。

设计理由见 [`integration-design.md`](integration-design.md)；后台日常操作见 [`admin.md`](admin.md)。

---

## 1. 制度换版（这一期最重要的变化）

### 1.1 以前的问题

同一 `doc_id` 换版本要"先删旧版 → 再传新版"，两步之间索引里没有这份制度，
员工问"我们制度怎么规定的"会直接拒答。真实制度每年都改，这个窗口期就是事故窗口。

### 1.2 现在怎么做

知识库页 → 上传 → **保持 `doc_id` 不变，把版本号 +1** → 上传。

系统在**同一个事务**里完成：新版入库（`active`）、旧版置为 `superseded`、触发重建。
重建期间问答仍用上一版索引，重建完成后原子热切换——**全程没有"制度不见了"的时刻**。

| 状态 | 含义 | 问答会用吗 |
|---|---|---|
| `active` | 现行版本 | ✅（且生效日已到） |
| `superseded` | 被新版替代，留档 | ❌ |
| `deleted` | 不要了（软删，文件保留） | ❌ |

### 1.3 三条硬规矩

**① 同 `doc_id` + 同版本重复上传会被拒绝**（`KB_003`）。
要改内容就提升版本号——否则"当时生效的是哪一版"就说不清了。
确实要就地改（比如文件传错了、还没人用），先删掉那一版再传。

**② 版本号是数字，不做大小比较。**
系统只用它判"是不是同一版"，不用它判"哪个更新"。传上来的就是新版。
展示用的版本串（`v1.0` / `2026-A`）填在「版本标识」里，与纸质文件对照。

**③ 待生效版本不进索引。**
`effective_from` 填未来日期时，这一版入库但不进索引，列表页显示「待生效」徽标。
这是设计行为：避免"下个月才生效的制度"本月就被检索到。

### 1.4 回滚

文档详情 → 版本历史 → 「回滚到本版」。

回滚不是删除：把旧版重新置为 `active`，当前版变 `superseded`，再重建索引。
新版写错了用这个，**不要用删除**——删掉会让制度整体消失，回滚则全程有依据。

### 1.5 只下掉某一版

路由 `POST /admin/kb/{doc_id}/delete` 接受可选 `version` 字段：

- 不传 `version`：该 `doc_id` 下所有 `active` 版本一起下线（"这份制度整体作废"）；
- 传了 `version`：只下线这一版，其他版本状态不变。

页面上「知识库 → 删除」对应的是前者（整份下线），因为那是更常见的动作；
"只退一版"用 1.4 的回滚即可，不需要单独按钮 —— 回滚还保留了依据，
直接删掉反而会让某些场景下制度短暂缺失。

有悬挂的 `active` 版本时，用 `payroll-check info` 与后台「历史版本」页核对即可。

## 2. 组织架构与部门统计

### 2.1 建部门（两级）

```bash
payroll-check dept add --name 华东区域 --code EC
payroll-check dept add --name SSC上海 --parent 华东区域
payroll-check dept list
```

只做两级是有意的：SSC 要回答的是"华东区这个月多少人在问冻结期、拒答率多少"，
两级够用；更深的组织树属于 HR 主数据，应该对接而不是自己造。

### 2.2 把员工挂到部门

```bash
payroll-check dept assign --username zhangsan --dept SSC上海
payroll-check dept assign --username zhangsan --dept SSC上海 --title 高级薪酬专员
```

`--dept` 可以写部门名或 id 前 8 位（列表里显示的就是这个）。
不传 `--title` 不会清空原岗位（只想调部门时用）。

### 2.3 看统计

后台概览页 → 「按部门看问答（近 30 天）」。

口径必须看清，否则数字会被误读：

| 项 | 口径 |
|---|---|
| 提问数 | **次数**，不是人数。一人问 10 次算 10 次 |
| 参与人数 | 该组有提问的**不同账号数** |
| 拒答率 | `refused / (answered + partial + refused)`，排除流式中的占位行 |
| 时间窗 | 固定近 30 天。全量口径会被上线头一个月的测试数据长期主导 |
| 未归属 | 没挂部门、或部门已被删的问答合成一组，名字就叫「未归属部门」 |

分组键用的是**部门表的 id**，不是用户表里的 `department_id`：
后者可能留着已删除部门的 id，拿它分组会得到两行都叫"未归属"、数字各算一半 ——
这是实测踩出来的，用例 `test_usage_by_department_sums_to_total` 守着它。

## 3. 语音输入

员工问答页输入框右侧的 🎙 按钮。

- **只在支持的浏览器出现**（Chrome / Edge）。Firefox / Safari 部分版本不支持，按钮直接隐藏。
- 用浏览器自带的 Web Speech API：**音频不出本机**，服务端没有任何改动。
- 识别结果**只填进输入框，不自动发送**。识别错一个字，检索就可能错一条条款，
  必须给用户"看一眼再按回车"的机会。
- 生成回答期间按钮禁用：识别文本会覆盖正在编辑的下一条问题。
- 权限被拒时只显示一行提示，不弹窗——语音是输入辅助，不该打断对话。

## 4. 对外集成接口 `/api/v1`

给 HR 系统、工单系统调用。**不是**内部 `/chat` 的复刻，两者职责不同：

| | 内部 `/chat` | 对外 `/api/v1/ask` |
|---|---|---|
| 凭证 | JWT（人的会话） | API Key（系统的凭证） |
| 形式 | SSE 流式 | 一次性 JSON |
| 会话 | 落库、多轮 | 无会话，靠 `history` 显式传 |
| 审计 | 进对话审计表 | 只记 Key 前缀与日志 |

### 4.1 签发 Key

```bash
payroll-check apikey add --name hr-portal --owner 张工 --rate-limit 60
payroll-check apikey list
payroll-check apikey revoke --id 3f2a1b0c          # 支持短 id
```

明文 **只打印一次**，库里只存 sha256。丢了就吊销重发——不要试图找回。

### 4.2 调用

```bash
curl -X POST http://127.0.0.1:8000/api/v1/ask \
  -H "Authorization: Bearer pcc_xxx" \
  -H "Content-Type: application/json" \
  -d '{"question":"冻结期内还能提交银行账户变更吗？"}'
```

```json
{
  "ok": true,
  "data": {
    "answer": "…… [2]",
    "status": "answered",
    "citations": [
      {"index": 2, "doc_id": "POL-CMP-2026-001", "doc_title": "员工薪酬变更核对制度",
       "clause_no": "第八条", "snippet": "……", "chunk_id": "…"}
    ],
    "query_used": "冻结期内还能提交银行账户变更吗？",
    "prompt_version": "v1",
    "model": "…",
    "latency_ms": 1820,
    "meta": {"guard": {"unverified_numbers": [], "invalid_citations": []}}
  }
}
```

`X-API-Key: pcc_xxx` 也支持（很多网关联调时只会配这个头）。

### 4.3 关于 `status`（调用方必须处理）

| status | 调用方该怎么做 |
|---|---|
| `answered` | 正常展示 |
| `partial` | 可展示，但加"部分内容需核对"提示；`meta.guard` 里有原因 |
| `refused` | **转人工**。这是"制度里没有依据"，不是一条答案 |
| `error` | 重试或转人工 |

把 `refused` 当普通答案展示给员工，等于让系统替公司说"不知道"，体验上比转人工差。

### 4.4 错误与限流

错误码与内部共用一套（`docs/api.md`）。对外常见：

| 码 | HTTP | 场景 |
|---|---|---|
| `AUTH_001` | 401 | 没带 Key / Key 错 / Key 被吊销（**不区分**，避免成为枚举接口） |
| `SRV_002` | 429 | 超过该 Key 的每分钟上限，`detail.retry_after` 是建议等待秒数 |
| `REQ_003` / `REQ_004` | 400 | 问题为空 / 过长（上限见 `api/schemas.py` 的 `MAX_QUESTION_CHARS`） |
| `IDX_001` | 503 | 索引没就绪（刚部署、重建失败） |

限流是**进程内滑动窗口**，多实例部署时实际上限 = 实例数 × 配额。
真要做全局配额，那是网关或 Redis 的事，不该塞在路由里。

### 4.5 健康检查

```bash
curl http://127.0.0.1:8000/api/v1/healthz -H "Authorization: Bearer pcc_xxx"
# {"ok":true,"data":{"ready":true,"chunk_count":20,"doc_count":1,"built_at":"...","rebuilding":false}}
```

只暴露"能不能用"需要的字段。库路径、密钥来源、重建细节都不给外部看。

## 5. 升级注意（0.3 → 0.4）

1. **数据库会自动迁移**：`policy_documents` 从 `doc_id` 单主键重建为 `(doc_id, version)` 唯一键，
   老数据整行搬过去（含切片数、时间戳），日志里会打印迁移了几行。
   **迁移在一个事务里，失败会整体回滚**，不会留下半张表。
2. **建议先备份** `data/chat.db`。迁移不可逆——虽然正确，但"能不能退回去"不该靠自信。
3. 迁移后 `version_label` 取原 `version` 的数字，界面上显示 `v1`。
   想要 `v1.0` 这种展示，重新上传时填「版本标识」，或直接改库。
4. 索引不需要手动重建，因为切片内容没变（内容哈希缓存会全部命中）。
5. `users` 表新增 `department_id`，老数据为 `NULL`，统计里落在「未归属部门」。

## 6. 已知限制

1. **历史版本的切片看不到**。索引只装现行版，旧版详情页会显示"这一版没有切片"。
   要对照历史切片，得保留旧索引产物（按 `version` 分目录），本期未做。
2. **部门两级**，不支持多级与历史沿革。
3. **语音只支持 Chrome / Edge**，且识别质量受浏览器与网络影响；不支持中文专有名词纠错。
4. **API Key 无过期时间**，只有"吊销"。定期轮换要靠人（建议写进运维日历）。
5. **限流是单实例语义**，见 4.4。
6. **外部接口不建会话**，多轮要调用方自己拼 `history`（最多取最近 6 条）。
