# 设计说明

> 面向要改这份代码的人。产品与需求背景见 `docs/product/`，接口契约见 `docs/api.md`。

## 1. 这个系统在解决什么

薪酬变更核对的核心风险不是"查不到制度"，而是**答得像制度、其实不在制度里**。

所以本项目的设计重心放在三件事上，而不是"把 LLM 接进来"：

| 目标 | 落地手段 |
|---|---|
| 答案必须能回到原文 | 每个切片挂 `doc_id + chunk_id + clause_range`，引用由系统生成，模型无权伪造 |
| 数字不由模型产出 | `core/guard.py` 把答案里带单位的数字逐个回查原文，查不到即降级 |
| 没有依据就闭嘴 | 检索层设"两路最高原始分"闸门，无证据直接拒答，不调用模型 |

非目标（阶段 1 明确不做）：Web 服务、多轮滚动摘要、权限与审计链、图谱多跳、真实 rerank 模型。

## 2. 分层

```
            ┌─────────────────────────────────────────┐
  入口层    │ main.py（CLI）/ api/（FastAPI：/chat SSE）│
            └───────────────────┬─────────────────────┘
                                │
            ┌───────────────────▼─────────────────────┐
  编排层    │ core/orchestrator.py                    │
            │ 检索 → 组装 prompt → 生成 → 护栏 → 引用  │
            └───┬───────────────┬─────────────────┬───┘
                │               │                 │
   检索层   ┌───▼────┐  ┌───────▼──────┐  ┌───────▼──────┐
            │ hybrid │  │ llm/ 适配层   │  │ guard.py     │
            │ (RRF)  │  │ (唯一出网口)  │  │ (程序化复核)  │
            └─┬────┬─┘  └───────┬──────┘  └──────────────┘
              │    │            │
        ┌─────▼┐ ┌─▼─────┐ ┌────▼─────┐
        │faiss │ │ bm25  │ │ http.py  │
        └──────┘ └───────┘ └──────────┘
                ▲
   摄入层   parser.py → chunker.py → pipeline.py

   持久层   store/db.py → store/chat_repo.py（只有这里写 SQL，被 api/ 调用）
```

依赖方向严格单向：`core` 不 import `main` 也不 import `api`；`api` 只做协议转换，SQL 全在 `store`。
这条规则让"把 CLI 换成 HTTP 服务"变成纯增量工作——阶段 2 落地时 `core/` 只改了
`orchestrator` 新增 `answer_stream()` 与 `entities` 加两个展示字段，检索与护栏一行未动。

## 4. 四个关键决策

### 4.1 切片：500 字是容量，不是刀口

朴素做法是 `text[i:i+500]`，后果是一条制度被切成两半，引用"第十三条"时那半条并不在命中的切片里。

本实现的做法是**按 500 字装箱，装箱单元是"条款"**：

1. 以"章"为硬边界，跨章绝不合并；
2. 一条放得下就继续放下一条，放不下在条款边界断开；
3. 表格是原子单元，整表不切（半张基数表必然导致编数字）；
4. "第X条 XXX"标题内联进正文，让切片能自证身份；
5. 只有同一条款被迫续切时才加 80 字重叠，且对齐到句首。

代价是切片长度不均（实测 81–471 字，均值 294），收益是**引用可举证**。这个取舍是刻意的：宁可长度不规则，也不要引用失真。

### 4.2 融合用 RRF，不用加权求和

向量余弦的取值范围是 0~1，BM25 是 0~30。直接相加等于让 BM25 单方面决定排序。

RRF 只看名次：`score = Σ wᵢ / (k + rankᵢ)`，天然免疫量纲，也不需要调归一化。副作用是**融合分本身不代表相关性强度** —— 这也是拒答闸门必须看两路原始分而不是融合分的原因。

### 4.3 拒答闸门看"两路最高原始分"

一条垃圾切片只要在两路都排第一，融合分照样最高。所以闸门判定的是：

```
if best_vector_score < MIN_VECTOR_SCORE and best_bm25_score < MIN_BM25_SCORE:
    拒答（不调用模型，0 token）
```

⚠️ **阈值与向量模型强绑定**。当前 `0.25 / 4.0` 是按 hash 占位向量标定的（有效问题向量分 0.27~0.38，越界问题 ≤0.12）。换成 bge-m3 这类真实模型后相关分会整体抬高，**必须重新标定**，否则会变成"该答的不答"。

### 4.4 护栏是程序化复核，不是 prompt 叮嘱

Prompt 里写"数字照抄"只是软约束。`guard.py` 做的是硬检查：

- **引用有效性**：角标必须指向真实存在的资料编号，且不能一个角标都没有；
- **数字可溯源**：抽出答案里所有带单位的数字，逐个回查原文，查不到就记 `unverified_numbers` 并降级 `partial`；
- **拒答识别**：模型合规拒答不该被当成异常，否则监控天天告警。

状态机：`answered` → `partial`（有告警）→ `refused`（模型明确拒答）。

## 5. 一次问答的完整链路

```
问题
 ├─ 向量通道：embed(question) → faiss.topk(12)
 ├─ 全文通道：tokenize(question) → bm25.topk(12)      ← 两路 tokenize 必须同一个函数
 ├─ RRF 融合 → 生效期过滤 → top3
 ├─ 闸门判定 ──拒绝──→ 返回 refused（不调用模型）
 ├─ 组装 prompt（编号 + 文档 + 条款 + chunk_id）
 ├─ LLM 生成（唯一出网口）
 ├─ 护栏复核 → answered / partial / refused
 └─ 组装 Citation（角标 → chunk_id 的映射权在系统手里）
```

## 6. 已知限制

1. **hash 向量没有语义能力**。默认配置只能跑通链路，不能评估质量。生产必须换真实向量模型。
2. **闸门只挡"明显越界"**。"制度相关但库里没有"的问法挡不住 —— 这类要靠 Router 意图分流（阶段 2）。
3. **BM25 是内存倒排**，千条切片内无感，上万条要换 `tsvector` 或独立的检索服务。
4. **单文档单版本**。多制度、多地区、多版本并存需要 `policy_documents` 表与版本流程（阶段 2）。
5. **评测集只有 8 题**，且由开发撰写。真正的验收要 HR 出 20 题以上，见 CI 里的阈值卡口。

## 7. 阶段规划

| 阶段 | 内容 | 本仓库现状 |
|---|---|---|
| 1 | 单文档 RAG：切片 → 混合检索 → 带引用回答 → 护栏 | ✅ 已完成 |
| 2 | 服务化：FastAPI、会话、Router 分流、pgvector、权限 | 待做；`core/` 可原样复用 |
| 3 | 变更单与制度条款自动比对（差异分级、人工核对队列） | 待做 |
| 4 | 图谱抽取与多跳推理 | 待做 |

拆分时的原则是"阶段 2 只加壳、不改核"：`core/` 下每个模块的接口都是按"将来被 HTTP 层调用"设计的。
